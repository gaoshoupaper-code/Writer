# 核心诉求

两个独立痛点：

1. **Trace 性能优化**：进化端测试过程中，trace 详情页随事件增多加载越来越慢，最终白屏进不去。需要设计一种机制根治该问题。用户明确要求"告诉我为什么会这么慢"（根因已在调研中定位，见下）。

2. **登录闪烁修复**：进化端反复闪烁登录页，有时直接闪出到登录页。需要修复。

## 已定位的根因（调研结论，待写入正式需求）

### Trace 慢（两个 O(N²) 瓶颈）
- 后端 `app/view/traces.py:137` `_reconstruct_incremental_inputs`：每个增量 llm_start × 全量事件 = O(M×N)
- 前端 `lib/trace.ts:11` `appendLiveTraceEvent`：每条 SSE 事件全量 filter+sort+重投影，累计 O(N²)
- 放大：后端详情接口无分页 / 前端时间线无虚拟滚动 / SQLite 单连接全局锁

### 登录闪烁
- 主因：`app/core/sso_auth.py:109-130` executor 不可达时误判 session 失效返回 401
- 放大：`lib/api.ts:130` 任意 401 全局跳登录 + Monitor 每 5s 4 路并发轮询
- 闪烁循环：Shell 守卫失败即跳登录且不重试 ↔ 登录页反向探测跳回首页，无去抖

## 第一轮确认（2026-07-11）

1. **Trace 规模**：上千~几千事件。
   → 约束：仅算法层消除 O(N²) **不够**，必须端到端分页 + 虚拟滚动 + 懒加载。算法优化只是基础。

2. **实时性**：需要实时，修好 SSE 数据流断点。
   → 约束：SSE 要从 evolution recorder 队列消费自产 trace（当前只拉 executor）；同时前端 SSE 消费的 O(N²) 必须一并解决（否则即使数据流通了，实时看也会卡死）。

3. **登录闪烁**：两种场景都有（测试时轮询触发 + 打开/切换页面时闪）。
   → 约束：端到端全修——后端 SSO 区分 503/401 + 前端 401 去抖 + 守卫重试 + 消除 Shell↔Login 反弹 + 考虑 session 持久化。

## 第二轮确认（2026-07-11）

4. **详情接口数据模型**：只返回 nodes/context/todos（投影后精简结果），events 按需懒加载（点开某 node 才拉对应原始事件）。
   → 后端重构深度：详情接口不再返回 events 数组；新增 events 懒加载接口（按 node/seq 范围查询）。前端抽屉改为打开时才请求。

5. **前端时间线渲染**：虚拟滚动（react-window），只渲染可视区域 node 行。
   → 约束：需引入 react-window（或等价）依赖；nodes 数组本身仍全量（nodes 是投影后精简结构，远小于 events），虚拟滚动只管 DOM 层。

6. **Session 持久化**：持久化到 Tauri Store，重启免登录。
   → 约束：Rust 端 cookie jar 启动时从 Store 恢复；需处理过期清理。

## 第三轮确认（2026-07-11）

7. **交付顺序**：先登录闪烁（影响面大、改动独立），后 trace 优化（架构重构）。

### SSE 推送内容：前端 vs 后端承担深度分析

**现状关键事实**（已通过代码确认）：
- recorder 运行期**完全不投影 node**，只在终态（complete/fail）一次性全量 DELETE+INSERT
- projector 是**纯函数式无状态全量重算**，`_ProjectionState` 全在方法局部变量，调用结束即丢
- projector 有回填（duration）+ 成对待匹配（llm_start→llm_end），意味着增量投影需支持 **node update**，不只是 append
- **仓库已有成熟的增量范式模板**：`compute_increment`/`IncrementState`（write 时算增量 + 重启降级），可直接对标
- 前端 `projectTraceDetail`（TS）和后端 `TraceProjector`（Python）是**两份独立投影实现**，必须手工保持一致

## 第四轮确认（2026-07-11）

8. **SSE 走向**：走向 A（后端增量投影，SSE 推 node patch，前端只做 append/update）。
   → 价值：根治双投影债（前端 TS + 后端 Python 两份投影合并为一份）+ 前端真正轻量（不持 events，只持 nodes）。
   → 约束：projector 需增量化改造（`_ProjectionState` 7字段持久化 + node update 支持 + context_sequence 跨调用连续）；对标仓库已有的 `compute_increment`/`IncrementState` 范式（含重启降级）。

9. **登录重试策略**：503/401 区分 + 静默重试。
   → 后端：SSO 中间件 executor 不可达时返 503（不返 401），session 真失效才返 401。
   → 前端：只对 401 跳登录，503 静默重试（不跳转、不闪烁）。
