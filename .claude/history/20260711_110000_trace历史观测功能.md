# Trace 历史观测功能 需求基准

## 核心诉求（Step 0 初稿，待用户确认）

在进化端桌面提供一个**历史 Trace 浏览能力**，让用户能：
1. 查看以前跑过的 trace（不只是当前活跃的）
2. 创作端 trace 和进化端 trace 分开展示
3. 按时间排序浏览
4. 能区分不同用户的 trace

### 现状对照（后端能力已就位，前端缺入口）

后端 `GET /api/traces` 已支持：多维度过滤（workspace/thread/status/owner/run_purpose）+ `started_at DESC` 排序 + limit/offset 分页。

前端 monitor.tsx 当前只展示**活跃 run**（5s 轮询 `getActiveRuns`），没有历史 trace 列表浏览入口。

### 已识别的盲区（待挖掘）

- **进化端 trace 的 owner 恒为 'unknown'**：recorder create_run 未填 owner_user_id 列，进化端无本地 user 表。
- **"区分用户"对进化端 trace 的含义**：进化端 trace 是谁产的？是否需要标识操作者？
- **历史 trace 的数据范围**：全部？最近 N 天？是否涉及保留策略。
- **功能入口与交互形式**：monitor 改造还是独立页面。

---

## 已确认决策

### D1：用户区分范围 —— 只对创作端 trace 区分用户 ✅
- 进化端 trace（`evolution_eval`/`evolution_evolve`）统一归"系统/进化端"一类，**不需要**区分操作者。
- 只有创作端 trace（`run_purpose=user_generation`）按真实 `owner_user_id` 区分用户。
- 这意味着后端无需改造 recorder 写入逻辑——`owner_user_id` 列现状（创作端有值、进化端 'unknown'）正好符合需求。

### D2：功能入口 —— 独立新页面"Trace 历史" ✅
- 侧边导航新增一个入口，与 monitor（活跃大盘）平级。
- monitor 继续只管活跃 run，历史观测是独立页面。

### D3：列表展示信息 ✅
历史列表展示以下列：
| 列 | 数据来源 | 说明 |
|----|---------|------|
| trace_id / session_name | runs 表 | 标识 |
| run_purpose 标签 | runs.run_purpose | 来源（创作/评估/进化） |
| owner_user_id | runs.owner_user_id | 用户（仅创作端有值） |
| status | runs.status | 结果（completed/failed/cancelled） |
| started_at + duration | runs.started_at / duration_ms | 时间维度 |
| event_count / 节点数 | runs.event_count / nodes 表 count | 规模 |

---

### D4：用户名展示 + 本地映射表 ✅
- 列表不显示原始 user_id 字符串，显示**用户名**。
- evolution 本地新建一张 **user 映射表**（user_id → username 等展示字段），定时从 executor 同步。
- 列表查询时 JOIN 或内存缓存查映射，渲染用户名。

### D5：点击 trace → 复用现有 trace-detail 页 ✅
- 点击历史列表行 → 跳转 `/trace/:trace_id`，复用现有 trace-detail.tsx。
- 终态 trace 不开 SSE 流（useTraceStream 已有非活跃判断），纯静态展示 DB 数据。

### D6：过滤维度 —— 用户 + 时间范围 ✅
- **owner（用户）过滤**：创作端视图下，按用户筛选。
- **时间范围过滤**：按时间缩小范围。
- ⚠️ 后端 `GET /api/traces` **当前不支持时间范围过滤**，需补 `since`/`until` 参数。

---

### D7：页面内双 Tab —— 创作历史 / 进化历史 ✅
- 新页面内部双 Tab，与 monitor 的双 Tab 体验一致。
- 创作历史 Tab：显示 `run_purpose=user_generation` 的 trace，显示用户筛选。
- 进化历史 Tab：显示 `run_purpose=evolution_eval/evolution_evolve` 的 trace，无用户筛选（统一归"系统"）。

### D8：时间范围过滤 —— 预设快捷按钮 ✅
- 交互形式："今天 / 最近7天 / 最近30天 / 全部" 预设按钮。
- 后端需补 `since`/`until` 时间范围过滤参数。

### D9：分页 —— 传统分页器 ✅
- 上一页/下一页/页码，每页 50 条（与后端默认 limit 一致）。

---

### D10：列表刷新 —— 纯手动刷新 ✅
- 进页面拉一次数据，之后手动点刷新按钮。
- 历史 trace 都是终态数据，不频繁变化。

### D11：权限 —— 不做行级隔离 ✅
- 能进 evolution 的白名单用户都能看所有 trace。
- 不需要后端改造行级过滤。

### D12：数据量 —— 小规模（< 1000 条）✅
- 每天产出 < 10 条 trace，limit=500 + 分页完全够用。
- `started_at` 无索引在小数据量下无性能压力，无需额外加索引。
- 不需要保留/清理策略。

### D13：用户映射表同步 —— 启动同步 + 每天定时刷新 ✅
- evolution 启动时（lifespan）从 executor 拉一次用户列表。
- 后台定时任务每天刷新一次。
- 映射表字段：`user_id`、`username`、`is_active`（够列表展示和映射用）。

### D14：排序 —— 固定按 started_at 倒序 ✅
- 最新在上，不支持正序切换。

### D15：进化端标识展示 —— session_name 优先，缺省 trace_id 缩写 ✅
- 有 session_name 就显示 session_name。
- 没有就显示 trace_id 缩写（如 `trc_a3f2...`）。
