# 需求：重构进化端两个 Agent

## 核心诉求

重构 evolution 端两个 DeepAgent，重新划定它们的能力边界与认知模型：

- **评估 Agent 做减法**：收窄为"纯 trace 评审"——只看 trace 做分析，剥离源码可见性与 Agent 要素可见性。
- **进化 Agent 做加法且扁平化**：去掉 plan/execute 双子代理，合并为单个 Agent；赋予它一套**完整的 Agent 要素全景认知**——能看全部源码、理解每个要素的位置与作用、新增 tool 与 State 两个要素、建立"State 字段须经 Middleware 操作"的约束意识。

## 现状基线（已探查确认）

### 评估 Agent（eval_agent/）
- 独立顶层 DeepAgent，无子代理。
- 10 工具分 4 组：trace（read_trace/read_trace_node/read_trace_range）、surface（read_surface + **read_source_file** 读源码）、content（get_content_score）、report（write_eval_report）。
- NoFilesystemToolsMiddleware 禁用框架自带 fs 工具。
- 产出 → evaluation_sessions 表（scores+findings+report_md）。

### 进化 Agent（evolve/driver/）
- driver 薄编排器 + 2 子代理：plan（设计方案，产 design_doc.md）+ execute（落地写码，产代码改动+change_log.md）。
- PhaseGuardMiddleware 锁 plan→execute 两阶段顺序。
- driver 自身 0 工具，靠 task 委托。
- plan 无专属读源码工具；execute 用框架自带 read_file/write_file/edit_file（FilesystemBackend 真落盘）。

### DeepAgent State / Middleware 机制
- State = 分层 TypedDict。messages 是核心；外加各 middleware 扩展字段（todos / memory / files / goal 等）。
- **Middleware 不直接改 State**：通过 hook 返回 dict、Command(update={...})、request.override() 三件套操作。
- State 当前字段（按来源）：
  - 基类：messages、jump_to、structured_response
  - TodoListMiddleware：todos（每项 {content, status}）
  - MemoryMiddleware：memory_contents
  - FilesystemMiddleware：files
  - 项目 GoalMiddleware：goal / goal_completed / goal_acceptance_evidence 等

## 已确认决策

### D1：评估 Agent 工具收窄为纯 trace 评审（2026-07-12）
- surface 整组删除：`read_surface`（读要素/设计意图）+ `read_source_file`（读源码全文）全删。
- 保留工具：trace 组（read_trace / read_trace_node / read_trace_range）+ content 组（get_content_score）+ report 组（write_eval_report）。
- 评估 Agent 对"Agent 是怎么搭的"和"源码长啥样"**完全无知**，只看执行轨迹。
- NoFilesystemToolsMiddleware 保留（继续禁用框架自带 fs 工具，防止绕道读源码）。

### D2：要素全景 = 完整运转机理（2026-07-12）
- 进化 Agent 的认知边界覆盖三层：
  1. **harness 包八要素**：manifest / prompts / skills / middleware / subagents / assemble + 新增 tool / 新增 State。
  2. **框架装配层**：create_deep_agent 参数（model/backend/checkpointer/middleware 挂载顺序/内置工具集/内置 middleware）。
  3. **运行时运转流程**：一次 ainvoke 从头到尾——消息进 State → middleware 链（before_model/wrap_model_call/after_model）→ LLM → 工具（wrap_tool_call）→ 回 State 的循环，直到结束。
- 进化 Agent 要能"像看透机器内部一样"理解 agent 怎么跑的。

### D3：进化 Agent 扁平化——单体、保留产出、删 PhaseGuard（2026-07-12）
- 去掉 plan/execute 双子代理，合并为**单个顶层 Agent**。
- 保留产出形态：design_doc.md + 代码改动 + change_log.md（下游审查链路不变）。
- 删除 PhaseGuardMiddleware（不再强制"先方案后落地"两阶段顺序）。
- Agent 在单次会话里自行决定编排——可先想后做、边想边做、迭代修改。

### D4：tool 要素 = 与 prompt/middleware 同级的一等要素（2026-07-12）
- 进化 Agent 把 `harnesses/current/tools/` 当作和 prompts/、middleware/ 平级的要素：
  - 能列出有哪些工具文件。
  - 能读每个工具的源码。
  - 理解工具怎么注册挂载到 agent（create_deep_agent(tools=[...])）。
  - 能修改/新增工具代码。
- 当前 tools/ 目录只有 goal.py 一个工具，但 tool 在认知层面被"立起来"成为一等要素。

### D5：能力边界 = 工具集（核心设计原则，2026-07-12）
- **进化 Agent 能做什么，完全由它挂载的工具集决定。**
  - **能动的要素** → 给对应的读/写工具（Agent 通过工具操作）。
  - **不能动的要素** → 没有对应工具（Agent 天然改不了，无法越界）。
  - **system prompt 里说明**：你能改哪些要素、不能改哪些要素、为什么。
- **State 字段属于"不能直接改"**：没有"直接改 State 字段"的工具。如果要让 Agent 能操作 State，唯一途径是给它一个"定义/修改 Middleware"的工具——因为 Middleware 才是 State 字段的合法操作者（hook 返回 dict / Command(update={...})）。
- 这意味着进化 Agent 的工具集设计 = 能力边界设计，是最核心的设计决策。

### D6：评估维度同步收窄（2026-07-12）
- 评估 Agent 删 surface 后，评估维度相应收窄：
  - 砍掉：涉及"设计意图/源码质量/要素合理性"的分析维度（如"设计 vs 实现偏差"）。
  - 保留：执行过程指标（流程硬指标）+ 产出内容质量（content_score）+ trace 中暴露的问题。
- 评估报告聚焦"这次执行跑得怎么样"，不再评"这个 Agent 设计得对不对"。

### D7：全景注入 = 详细 prompt + 探查工具（2026-07-12）
- system_prompt 写较详细的要素全景知识（八要素各自是什么、起什么作用、在运转流程的什么位置、create_deep_agent 怎么装配、一次 ainvoke 怎么流转），足够 Agent 理解运转机理。
- 同时提供只读探查工具，用于查"当前包里实际有什么"（因为 prompt 里的全景是抽象知识，实际文件清单是动态的）：
  - 列出八要素及当前文件清单。
  - 读某要素的源码内容。
  - 查 State 字段结构（schema）。

### D8：Middleware 工具 = 自由写代码（2026-07-12）
- 进化 Agent 通过"写 Middleware 源码"的方式操作 State——产出符合 DeepAgent AgentMiddleware 规范的 Python 代码（含 state_schema / hook / 返回 dict），写入 harnesses/current/middleware/。
- 能力最强，可表达任意 state 操作逻辑。
- 风险控制：靠 validate_changes（语法/导入校验）兜底，靠 system_prompt 讲明规范。

### D9：可改要素清单（2026-07-12，完整版）
进化 Agent 对各要素的写能力分配（"工具集 = 能力边界"原则落地）：

| 要素 | 权限 | 说明 |
|------|------|------|
| **prompts** | ✓ 可改 | 进化主要对象，配写工具 |
| **middleware** | ✓ 可改 | 改护栏/state 逻辑（含自由写新 middleware 代码，D8） |
| **tool** | ✓ 可改 | 新增/修改 agent 工具源码 |
| **subagents** | ✓ 可改 | 改子代理定义（用户明确要求） |
| **skills** | ✓ 可改 | 新增/修改技能包 |
| **assemble** | 只读 | 可读 assemble 源码理解装配机制，不可改（D10 废弃 config 驱动后，assemble 不再有任何写途径） |
| **State** | 不可直接改 | 只读探查 schema；操作 State 唯一途径 = 定义/改 Middleware（D8） |
| **manifest** | 不可见 | 连看都不看，对进化无用。版本号/change_summary 等由进化系统自动维护 |

**权限分层总结**：
- 可改（5 个，配写工具）：prompts / middleware / tool / subagents / skills
- 只读探查（2 个）：assemble（读源码理解装配）、State（读 schema 理解字段）
- 不可见（1 个）：manifest

### D10：改 agent 走专用写工具写源码，废弃 config 驱动（2026-07-12）
- 统一用"专用写工具写源码"模式，废弃原 execute 的 apply_edits config 驱动机制。
- 每个可改要素配一个专用写工具（不是裸 write_file，而是包了路径锁定 + 校验 + 记录的接口），内部写源码文件到 harnesses/current/ 对应目录。
- 设计原则：安全、结构化、可追溯，且能改源码（覆盖 config 机制覆盖不到的 middleware 源码 / tool / subagent）。

### D11：进化 Agent 工具集设计 = 读粗写细混合（2026-07-12）
**只读探查工具（粗粒度，给认知）**：
- list_elements — 列出八要素及当前文件清单
- read_source — 读任意要素源码（参数指定路径）
- inspect_state_schema — 查 State 字段结构（只读 schema）
- read_assemble — 读 assemble 源码理解装配机制

**写操作工具（细粒度，每可改要素一个，给受控能力）**：
- write_prompt(name, content) — 写 prompts/{name}.md
- write_middleware(name, code) — 写 middleware/{name}.py（含语法/导入校验）
- write_tool(name, code) — 写 tools/{name}.py
- write_skill(path, content) — 写 skills/...
- write_subagent(name, code) — 写 subagents/{name}.py

**流程工具（从原 plan/execute 归并）**：
- read_eval_report — 读评估报告
- read_trace — 读 trace 摘要
- write_design_doc — 写 design_doc.md（产出保留 D3）
- validate_changes — 校验改动合法性（语法/import/契约）
- write_change_log — 写 change_log.md（产出保留 D3）

### D13：落盘方式 = 专用工具封装框架 backend（2026-07-12）
- 专用写工具内部调用 DeepAgent 框架的 FilesystemBackend 接口（write/edit/read）落盘，不裸 pathlib。
- 架构定位：专用工具 = 框架 backend 的**语义层封装**——外层做要素分派 + 语义校验，中层复用框架的路径安全（virtual_mode 越界拦截 + symlink 防护 + O_NOFOLLOW），底层是 OS IO。
- 进化 Agent 挂 FilesystemBackend(root_dir=harnesses/current/, virtual_mode=True)。
- **约束处理**：FilesystemBackend.write() 拒绝覆盖已存在文件。专用写工具区分两种模式：
  - 新建文件 → 调 backend.write()
  - 修改已有文件 → 调 backend.edit()（精确替换）或先 read 再全量重写
- FilesystemMiddleware 仍挂载（backend 的载体），但框架自带 fs 工具被 NoFilesystemToolsMiddleware 过滤——backend 只服务专用工具的内部调用。
