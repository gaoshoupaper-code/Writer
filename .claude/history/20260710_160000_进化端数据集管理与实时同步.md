# 进化端数据集管理与实时同步 — 需求基准报告（已冻结）

## 核心诉求

重构进化端数据集的"数据 → 同步 → 桌面端展示"链路，保证维护者在桌面端**始终能可靠看到服务器上 golden 和 growing 两层的完整数据**，彻底消除当前"数据丢失"和"列表变空"的隐患。

## 决策记录

### 第 1-2 轮：范围收缩
- 初始诉求"两层增删改查"经分析后撤销
- 用户明确：golden 改 demand 会破坏 benchmark 可比性 → **golden 只读**
- 写入能力（编辑/删除/新建）本轮不做，后续再说
- 实时性：**手动刷新即可**（非轮询/推送）

### 第 3-4 轮：重构决策
- 用户态度：**不要打补丁，要重构存储架构**（已修一天未根治）
- 部署环境：**仅生产用 Docker**
- golden 权威数据源：**git 仓库**（跟着代码走）
- 需求范围：golden + growing 两层都要可靠查看

## 已确认需求

### R1. 数据可靠性（核心，重构存储架构）
**目标：消灭数据丢失。** 当前的"数据丢失"和"列表变空"根源是存储架构缺陷（两套互相矛盾的数据源），不是接口 bug。

**需求：**
- golden 的权威源是 **git 仓库**（`evolution/data/evalset/golden/`），随代码/镜像更新，运行时只读
- growing 的权威源是 **volume**（运行时 promote 写入的数据），持久化不丢
- 消除"镜像 seed 覆盖 volume"的矛盾——不再有两套互相覆盖的 golden 数据源
- Docker 容器重启/重建后，数据状态可预期、不丢失

### R2. 桌面端可靠查看
**目标：保证看得见、看得对。**

**需求：**
- GoldenTab / GrowingTab 能完整、正确显示服务器的 case 列表和详情
- 列表请求失败时**不能静默显示为空列表**，要明确提示"加载失败"（消除"分不清真没数据还是出错"）
- 提供**手动刷新**能力（刷新按钮），用户点一下即可拉取最新
- golden revision 信息条失败时给出提示，不静默消失

### R3. 鉴权（约束，沿用现有）
- 所有数据集相关接口延续现有模式，**无需新增加密/鉴权机制**
- 仅维护者可执行写入操作（本轮暂无写入，但预留约束）

## 约束条件（给设计阶段的输入，非需求）

| 约束 | 说明 |
|---|---|
| C1. 仅生产走 Docker | 重构方案只需保证 Docker 部署路径正确，本地开发可不考虑 Docker |
| C2. git 仓库为 golden 权威源 | 影响 promote（升级 golden）流程——必须从"运行时写目录"改为"git 提交流程"，否则运行时升级的数据进不了 git 权威源。这是设计阶段要解决的关键矛盾 |
| C3. 本轮只读 | 不做编辑/删除/新建 UI，但存储架构重构要为未来写入能力留空间（不堵死） |
| C4. benchmark 语义不变 | golden 仍是冻结基准，revision 指纹机制保留 |
| C5. 保持已有正确部分 | 文件系统为真源 + DB 补元数据的降级设计、revision 指纹计算、Rust 中继请求——这些是对的，不要推倒重来 |

## 已知问题清单（重构必须解决）

### 🔴 根源（存储架构缺陷，导致数据丢失）
- **P1** Docker entrypoint 每次重启用镜像 seed 无条件覆盖 golden 目录（`docker-entrypoint.sh:27-28`），运行时升级到 golden 的 case 丢失
- **P2** golden 数据源分裂为镜像 seed（随 build）vs volume（运行时），两套互相矛盾，无单一权威源
- **P5** 列表 API 文件系统扫描无 try/except（`api.py:37`），目录异常时 500 → 前端列表变空

### 🟡 链路不顺畅（桌面端展示）
- **P8** 前端请求失败静默吞成空列表（`GoldenTab.tsx:24` / `GrowingTab.tsx:23`），用户分不清"无数据"还是"出错"
- **P9** 无刷新按钮、无轮询（`GoldenTab.tsx:36`），服务端变更后桌面端不刷新
- **P10** 切Tab刷新依赖 Radix 卸载（`dataset.tsx:25`），脆弱
- **P11** revision 拉取失败信息条静默消失（`GoldenTab.tsx:25`）

### 🟡 次要隐患
- **P3** growing 层只在 volume，首次部署镜像里的 growing case 不进 volume
- **P6** revision 计算与 case 列表两套独立扫描逻辑，可能不一致
- **P12** 改 golden 必须 rebuild 镜像才能让 seed 更新，流程重
- **P13** commit e8ecd4a 的修复是 API 层补丁，未根治存储层缺陷

1. Docker 容器重启/重建后，golden 和 growing 两层的数据**不丢失、状态可预期**
2. 桌面端 GoldenTab/GrowingTab 能完整显示服务器真实存在的所有 case
3. 列表加载失败时**明确提示错误**，不显示为空列表
4. 桌面端有**刷新按钮**，点击后立即拉取最新数据
5. golden 数据来源**唯一且明确**（git 仓库），不再有 seed vs volume 的矛盾
