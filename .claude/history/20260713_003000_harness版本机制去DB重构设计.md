# 设计：harness 版本机制去 DB 重构

## 需求基准（来自 require，已冻结）

- harness 完全独立 git 仓库；主仓库 .gitignore 不碰内容
- production = harness 仓库 main 分支；executor pull main（现有机制不变）
- registry.json 随版本进 git，记录谱系/评分/回滚日志
- 回滚 = git revert（线性前进）
- 版本编号 = 递增整数 v1/v2/v3
- evolution.db 砍掉 harness_snapshots + version_changes；trace/评估/会话保留
- executor 同步 = push(/reload) + 周期 reconcile
- 门控 = 分阶段（当前静态校验，预留 eval 接入点）

## 现状架构认知（设计基线）

### 已存在且可复用的机制
- `evolution/app/core/git_ops.py`：commit_and_push / current_commit / show_file / init_work_repo —— git 操作已完备
- `executor/app/platform/agent/git_sync.py`：pull_production / checkout_commit —— executor pull 已完备
- `executor/app/platform/agent/loader.py`：load_current_package / reload_current —— 热加载已完备
- `executor/app/routers/internal.py` /reload 端点 —— push 通知已完备

### 要拆掉/改写的
- `evolution/app/versioning/snapshot_repo.py`：publish_config（DB INSERT）→ 改写为写 registry.json
- `evolution/app/versioning/version_changes_repo.py`：version_changes 表 → 合并进 registry.json
- `evolution/app/versioning/config_diff.py`：diff 计算 → 改为基于 git diff（registry 记摘要）
- DB schema：harness_snapshots + version_changes 两表 DROP
- 前端 API：/api/snapshots、/api/snapshots/production、/api/versions/{v} → 改读 registry.json

### 核心数据流（重构后）
```
evolution 端:
  harnesses/current/ (工作目录)
       ↓ commit_and_push(message)        ← git_ops.py 现有
  harness-repo (独立 git 仓库)
       ├── prompts/ middleware/ ...      ← 内容
       ├── __init__.py
       └── registry.json                 ← 版本注册表（新增）
       ↓ publish 时更新 registry.json + commit + push main
  executor /reload (push 通知)

executor 端:
  pull main → load_package → 读 registry.json（如需版本信息）
```

## 已确认设计决策（D1 轮）

### 发布原子性 = 单 commit
发布 = evolution 先改源码 + 更新 registry.json，再 `git add -A && commit && push`。一个 commit 同时包含源码改动和 registry 更新，天然原子，不会脱节。

### registry.json 结构 = 快照式
```jsonc
{
  "schema_version": 1,
  "production": 3,                    // 当前生产版本号（指针）
  "versions": [
    {
      "version": 1,
      "commit": "2782f1c",           // 该版本的 git commit short hash
      "parent_version": null,         // 谱系
      "change_summary": "初始包",
      "eval_score": null,             // 评估分（eval 成熟后填）
      "eval_status": "pending",       // pending | passed | failed
      "created_at": "2026-06-23T20:00:00Z",
      "source_session": null          // 产出该版本的 evolve session_id
    },
    { "version": 2, "commit": "98fc128", "parent_version": 1, ... },
    { "version": 3, "commit": "b8a171d", "parent_version": 2, ... }
  ],
  "rollback_log": [
    // 回滚事件日志（何时、从哪回退到哪、原因）
    // { "at": "...", "from": 3, "to": 2, "reason": "质量退化" }
  ]
}
```
- 几百~几千版本 = JSON 几百 KB ~ 几 MB，完全可接受（对比 DB config_json 单条就 29KB）
- 覆盖写入（每次发布/回滚重写整个文件），git 天然保留所有历史版本

## D3 重大发现：config 驱动装配是死代码

### 调查结论（代码级确认）
- executor 生产路径 `agent.py:171` 调 `pkg.assemble(ctx)`——**不传 config**，走硬编码路径
- `current/__init__.py` 的 `use_config=True` 分支（config 驱动）**从未被调用**——死代码
- `executor/app/platform/agent/assembler.py` 的 `build_middleware_list` **无任何调用者**——死代码
- `bootstrap.py` 的 `build_v1_config()` 生成的 config 存进 DB，但 executor **从不读它**
- config 驱动是"compose 配置化"的半成品设计，未落地

### 含义
- 去掉 DB config_json **对 executor 零影响**——executor 本来就只读 `prompts/*.md` + 硬编码 middleware
- 不需要为"config 从哪来"设计任何机制
- 这套死代码（assembler.py + __init__.py 的 use_config 分支 + bootstrap config 生成）**应该一并清理**（零技术债原则）

## D3a 已确认：config 驱动死代码一并清理

清理范围：
- `executor/app/platform/agent/assembler.py`（build_middleware_list 无调用者）
- `current/__init__.py` 的 `use_config=True` 分支（从未被调用）
- `evolution/app/harness_config/bootstrap.py`（build_v1_config 生成死 config）
- `evolution/app/harness_config/edits.py`（config edits 回放）
- `evolution/app/harness_config/config.py`（config 序列化/校验）
- `evolution/app/harness_config/class_ref.py`
- `evolution/app/versioning/config_diff.py`（config diff 计算）
- `evolution/app/versioning/version_changes_repo.py`（version_changes 表访问）

## publish_session 重构后的流程（6步→4步）

当前 7 步 → 重构后 4 步：
1. ~~git commit + push~~ → **保留**：`git_ops.commit_and_push()`
2. ~~构建 config（bootstrap+edits）~~ → **删除**（死代码）
3. ~~publish_config（DB INSERT）~~ → **改写**：更新 registry.json（append 版本 + 移 production 指针）+ 再 commit（含 registry 变更）
4. ~~通知 executor~~ → **保留**：`notify_executor()`
5. ~~存 version_changes intent~~ → **合并**：进 registry.json 该版本条目的 change_summary
6. ~~推进 session status~~ → **保留**：evolve_sessions 留 DB

## D2 已确认：git fast-forward 兜底

并发保护靠 git push 的 fast-forward 机制：registry 读-改-写放 commit 前，如果并发第二个 push 被 reject，pull 重试即可。进化发版人工触发，并发概率极低，不过度工程。

## D4 已确认：前端要素视图保留，数据源换 git

### 调查结论
- 前端 `harness.tsx`（Agent 要素透视页）**确实在用** getElements/getVersionDetail
- 但数据来自死代码 config_json，展示的"Agent 怎么搭的"**可能和实际运行的不一致**（割裂的另一种表现）

### 重构方案：数据源从 DB config → git 真实源文件
要素视图的本质是"这个版本的 Agent 有哪些 prompt/skill/middleware"，这些**就是 git 里的真实文件**：
- Prompt 要素 → 读 `prompts/*.md`（git show <commit>:prompts/xxx.md）
- Skills 要素 → 读 `skills/` 目录结构
- Middleware 要素 → 读 `middleware/*.py`（类名提取）

API 改造：
- `GET /snapshots` → 读 registry.json 的 versions 数组
- `GET /snapshots/production` → 读 registry.json 的 production 指针
- `GET /snapshots/{version}/elements` → 读 git（该 commit 的源文件）
- `GET /versions/{version}` → registry.json 元数据 + git diff（v_n vs v_parent）

### 含义
- 要素视图变得更准确（读真实文件而非死代码 config）
- diff 从 config_diff 计算改为 git diff（更精确，文件级 diff）

## D5/D6 已确认

- D5：**单 PR 一次到位**。一次部署切换，最干净，不留中间态。
- D6：**executor reconcile 每 10 分钟**。后台 git fetch 比较 commit hash，变了就 reload。

## 最终架构快照（所有决策已落地）

```
evolution/harnesses/
├── repo/                           ← 独立 git 仓库（新建，替代 current/）
│   ├── .git/                       ← 它自己的 git 历史（只装 harness 内容）
│   ├── prompts/                    ← harness 源码
│   ├── middleware/
│   ├── skills/
│   ├── subagents/
│   ├── tools/
│   ├── __init__.py                 ← assemble(ctx) 入口（删 use_config 分支）
│   └── registry.json               ← 版本注册表（新增）
│
└── （current/ 迁移后删除，harness.git 清理删除）

主仓库 Writer/
└── .gitignore 新增: evolution/harnesses/repo/
    （主仓库不跟踪 harness 内容，代码里只有路径引用）

evolution/harnesses/repo/ 的 bare 副本:
└── evolution/harness.git/          ← 重建为真正的 bare repo（只装 harness）

数据流:
  evolution 写: repo/ 改源码 + 更新 registry.json → commit_and_push → bare repo
  executor 读: pull_production() → git reset --hard origin/main → load_package → assemble(ctx)
  reconcile:   后台每10分钟 git fetch 比较 commit，变了 reload
  回滚:        git revert（main 线性前进），registry 记 rollback_log
  版本查询:    registry.json（版本列表/谱系/评分）+ git show/diff（要素视图）
```
