# Harness 要素页改造需求

## 核心诉求

把"Agent 要素"页面改造成"harness 能进化要素"的**完整、统一、直观**展示页。

一句话：让产品负责人（A 角色）一眼看清"这个版本的 harness 里，有哪些可被进化的要素、每一类长什么样、记忆流水线怎么运转"。

## 三大决策（已和用户确认）

### 决策 1：页面标题改名 → "Harness"

- **改名范围（用户选最彻底）**：前端展示文案 + TS 类型名 + 后端 API 路径**全部同步重命名**。
- 页面 h1：`Agent 要素` → `Harness 要素`（或 `Harness`，待定）。
- 导航/侧边栏：同步改名。
- TS 类型：`AgentElementView` → `HarnessElementView`；`ElementsView` → `HarnessElementsView`；`getElements()` → `getHarnessElements()`（前端 API 封装）。
- 后端 API 路径：`GET /api/snapshots/{v}/elements` → `GET /api/snapshots/{v}/harness-elements`。
- **约束**：记忆子系统接口路径改名 → 见 D1。
- 版本兼容性：直接 breaking，不保留旧路径 → 见 D2。

### 决策 2：新增 Tools Tab（独立子栏）

- **范围（用户选）**：Tools Tab 只展示**非记忆类**工具，记忆类工具专属记忆 Tab（避免重复展示）。
- Tools Tab 内每条工具的展示字段（参考 Skills Tab 格式，待最终确认）：
  - `path`：如 `tools/web_search.py`
  - `name`：函数/工具名
  - `description`：工具描述（来自 docstring 或 manifest）
  - `params`：入参 schema（可选，是否展开）
  - `load_error`：加载失败时展示 ⚠（对齐 Skills）
- **约束（数据来源）**：后端 `elements_api.get_elements` 当前不扫描 tools/ 目录，需新增 tools 扫描逻辑。
- **约束（去重规则）**：什么是"记忆类工具"？硬编码清单在 `constants.py:MEMORY_FILES`（path → file_role）里凡是 `type=="tool"` 的项。Tools Tab 扫描结果减去这些 path 即为"非记忆类工具"。
- **约束（diff 支持）**：Tools Tab 支持 added/removed 高亮，对齐 Skills Tab → 见 D3。

### 决策 3：记忆子系统改为统一 Tab 容器（保留流水线叙事）

- **形态（用户选）**：记忆子系统从"顶部独立大卡片"降级为**第 5 个 Tab**，但 **Tab 内部保留 4 阶段流水线视图**（抽取→存储→检索→回填）。
- 视觉一致性体现在"**都是 Tab**"，每个 Tab 内部按自己的最佳形态展示（Prompt 是文本块、Middleware 是泳道图、Memory 是流水线图）。
- **约束**：流水线视图当前由 `MemorySubsystemCard.tsx` 实现，需要把它从"整页顶部卡片"迁移到 Tab body 里。
- **约束（空态）**：早期版本（早于 NWM 重构）没有记忆子系统，记忆 Tab 需保留"此版本无记忆子系统"空态。
- **约束（diff 支持）**：Memory 流水线只标"某阶段文件被替换"的节点，不做行级 diff → 见 D3。

## Tab 最终顺序（已定 ✅）

按构造递进：`Prompt → Skills → Tools → Middleware → Memory`

## 已澄清（D 系列 ✅）

- **D1 ✅**：`/memory-elements` 路径**统一改名**为 **`/harness-elements/memory`**（嵌套式，语义是"harness-elements 里的 memory 子视图"，未来扩展优雅）。
- **D2 ✅**：**直接 breaking**，不保留旧路径 `/elements`。桌面 App 和后端同 release 部署，无版本错配风险。
- **D3 ✅→部分作废（设计阶段查证）**：
  - **原决策**：Tools 做 added/removed 高亮；Memory 只标节点替换。
  - **查证后推翻**：整个 diff 管道当前是死的（后端不返回 changes、version_changes 表已 DROP、前端静默失效）。
  - **修正决策**：本次**不做任何 diff 高亮**。Tools Tab 和 Memory 流水线都只做静态展示。diff 功能修复作为独立后续需求。
- **D4 ✅**：Tab 顺序按**构造递进**：`Prompt → Skills → Tools → Middleware → Memory`。

## 已澄清（D5–D7 深层模糊点 ✅）

- **D5 ❌ 作废（设计阶段查证后推翻）**：原"按两版本 MEMORY_FILES 并集过滤"前提错误。
  - **真相**：harness `tools/` 目录共 5 个文件，其中 4 个属记忆系统（已被 MEMORY_FILES 覆盖）、1 个属 meta agent（goal.py）。按 D5 过滤后 Tools Tab 几乎空，违背"看见 harness 全部 tools"的初衷。
  - **修正决策（设计阶段）**：Tools Tab **全展** tools/ 下所有文件，每个用 `scope` 标注真实归属（global/middleware/agent/memory），与 Memory Tab（流水线视角）互补。废除过滤。
- **D6 ✅ Tools 展示粒度**：**按文件**（一行一个 `tools/*.py`），和 Skills Tab 完全对齐。
- **D7 ✅→作废（依赖 D3，diff 管道死）**：Memory 节点替换标记本次不做。

## 新发现的技术约束（基于后端代码核实）

1. **后端扫描 `tools/` 目录在技术上可行**：`elements_api.py` 已有 `_list_files_at_commit(commit, subdir)` 辅助函数，新增 tools 扫描复用此模式即可（仿照 `_build_skill_infos` 写 `_build_tool_infos`）。
2. **MEMORY_FILES 里 type=="tool" 的有 4 个**（需被 Tools Tab 排除）：
   - `tools/narrative_schema.py`（store）
   - `tools/query_builder.py`（retrieve）
   - `tools/join_rules.py`（retrieve）
   - `tools/packet_formatter.py`（retrieve）
3. **⚠️ 新模糊点 D8（Tools 描述来源）**：Skills Tab 的描述来自 SKILL.md 的 YAML frontmatter（标准格式）。但 `.py` 文件没有标准 frontmatter，Tools 的 `description` 字段从哪来？候选：
   - **a. 模块 docstring**（文件首行 `"""..."""`）——Python 标准，但依赖开发者写
   - **b. harness manifest.json**——但 manifest 是打包清单，不一定有每个 tool 的描述
   - **c. 不展示描述，只展示 path**——最简单，但信息量少
   → 见下方 D8 待澄清。

## 边角场景（沿用既有模式，无需用户决策）

- **Tools Tab 空态**：某版本 `tools/` 目录为空、或所有 tool 都属于 MEMORY_FILES（全被过滤）时，显示"此版本无非记忆类工具"。对齐 MemorySubsystemCard 的空态模式。
- **Tools Tab 加载失败**：某 `.py` 解析失败（语法错误/docstring 提取异常）→ 展示 path + `⚠ load_error`，对齐 SkillsTab 的 `load_error` 模式。
- **Memory Tab 空态**：早于 NWM 重构的版本，显示"此版本无记忆子系统（早于 NWM 重构）"。沿用 MemorySubsystemCard 现有空态文案。
