# 创作端对话执行 UX 重设计

## 核心诉求（待用户确认）

用户反馈：**创作端在 Agent 执行过程中的 UI 体验不够好**。具体关切面——状态展示、命名、元素出现时机、用户体感——需要在现有基础上做一次系统性重设计，产出"一套专门的功能组件"。这是最直接关乎用户体验的环节。

> 当前理解的一句话概括：**用户发起一次创作请求后，从"按发送"到"拿到结果"这整段等待与交互过程，目前的信息反馈不够清晰、不够生动、不够让人安心，需要重新设计这段体验。**

## 现状基线（代码勘察，作为讨论起点）

### 现有的执行过程展示链路
1. 用户发送 → 追加占位 assistant message（`content: "正在执行..."`）→ SSE 流开启
2. 执行中主视图：**StageFlowView**（嵌在 assistant message 内）—— 折叠态显示状态圆点 + 焦点文案 + StageTrail 缩略链；展开态显示阶段列表（序号/标签/Badge/子代理任务数/工具调用数/耗时/substeps/思考摘要）
3. 兜底：无阶段卡但有工具 running 时，显示纯文字 `"正在处理…"`
4. 完成态：assistant message `status: completed`；正文 markdown 渲染
5. 异常态：failed/stopped → 显示"↻ 重试"按钮
6. HITL 中断：`awaitingInput` → 渲染 InterviewOptions 或 ImageReviewCard
7. 底部 composer：loading 时发送按钮变"生成中"，出现红色"停止"按钮

### 现有的状态指示器
- 脉动圆点（`stage-pulse` 1.2s / `pulse-dot` 1.4s）
- shimmer 骨架（Skeleton，仅最后一条 assistant 无 content 时）
- 动态焦点文案（如"正在写第 3 章·约 800 字"）
- **没有** spinner、进度条、百分比、思考流式输出、逐 token 打字效果

### 现状的关键观察（影响重设计的约束）
- 架构是"展示/逻辑分离"：所有执行编排/state/SSE 解析都在 `home.tsx`（1826 行上帝组件），ChatPanel 等都是纯展示组件
- 工具执行展示已从"逐工具气泡"演进到"阶段流聚合"，旧 `.tool-status` 气泡 CSS 是死代码
- 主对话流里**没有** chain-of-thought 逐 token 思考流，只有阶段性摘要（`stage.summary`）
- 更详细的 trace 在独立的 TracePanel（不在对话流内）
- 数据来源是后端 SSE：`model_stream` / `tool_call` / `tool_output` / `tool_error` / `trace_event` / `trace_snapshot` / `interrupt` / `final` / `credit_exhausted`

## 已确认的需求共识（第 1 轮）

### 重设计的核心理念
- **三大痛点（多选确认）**：① 状态/术语难懂 ② 等待时的焦虑感 ③ 交互断裂/卡顿感
- **明确不是痛点**：过程不透明/不可信 → **结论：不要往"给用户看更多 raw 信息"的方向走**。要的是"更友好、更安心、更顺滑"，不是"更透明"。
- 一句话：**把"冷的状态报表"重做成"一个有温度的 AI 写作伙伴在工作的过程"。**

### 目标用户
- **普通写作者**（非技术背景）
- 含义：术语要去技术化；专业指标（子代理任务数、工具调用次数、trace 节点）默认隐藏或折叠；信息密度要让普通人看得懂、不焦虑。

### 改造范围
- **最大档**：连执行编排一起重构。
- 允许动：`home.tsx` 的 SSE 处理、状态结构、甚至抽 store；允许动 ChatPanel / StageFlowView 的全部展示逻辑。
- 需求文档需记录：重构的**目标约束**（为什么重构、重构到什么程度算好），但不写具体方案（HOW）。

### 用户原话里的三个关键词（重要线索）
用户原始需求明确提到要考虑：**"什么状态、什么名字、什么时候出现"**。
- "什么状态" → 状态体系要重新设计（去术语化、拟人化）
- "什么名字" → Agent 可能有命名/人格的概念（待深挖）
- "什么时候出现" → 元素的出现时机与过渡动画编排（待深挖）

### 焦虑解法 / Agent 人格 / 重构动机（第 2 轮确认）

**① 焦虑解法 = 信息丰富化**
- 方向：让用户持续看到微小进展（思考流、预估时间、实时字数、当前动作）。
- **关键约束（与去术语化的内在张力）**：信息要丰富，但呈现必须去技术化、拟人化。
  - 反例：`tool_call: write_chapter · subagent: writing`
  - 正例：`小衍正在动笔写第 3 章……`
- → "小衍"人格的核心职责：做技术信息 → 人话的"翻译壳"。

**② Agent 人格 = 有名字有温度，叫"小衍"**
- 固定品牌化命名：**小衍**
- 第一人称"我"说话，像写作伙伴
- 这是全局体验的温度基调

**③ 重构动机 = 双驱动**
- 既为新 UI 铺路（支撑思考流、预估时间等新数据）
- 又有独立的可维护性价值（拆 home.tsx 1826 行上帝组件、抽状态机）
- 含义：设计文档需兼顾两条线——不能只写 UI 改动，也要写编排层重构目标。但 HOW（具体怎么拆、抽什么 store）留给设计阶段。

### 信息丰富化的具体形态（第 3 轮确认）

**① 思考流 = 要真正的 reasoning token 流式**
- 形态：小衍的思考过程实时流式显示（类似 ChatGPT/Claude 的 thinking 流）。
- **约束：需后端改造**——模型需吐 reasoning token，DeepAgent 需转发，SSE 需新增事件类型（如 `reasoning_stream`）。
- 纳入本次重构范围（前后端都要动）。

**② 预估时间 = 后端推预估值**
- 后端根据任务规模估算并推送预估时间/预估字数。
- **约束：需改后端 SSE 契约**，新增预估字段。
- 纳入本次重构范围。

**③ 进度表达（多选）= 字数进度 + 动态文案轮播 + 脉动动画，三者结合**
- **字数进度**：已写 X 字 / 目标 Y 字。对正文阶段特别有用。
- **动态文案轮播**：一句话描述当前动作（"小衍正在构思情节" → "正在动笔写第 3 章"），随状态变化。
- **脉动动画/呼吸感**：纯视觉"活着"感（呼吸灯/波纹/笔尖动画），不带具体进度信息。
- 明确**不要**阶段进度条（Step 1/5）——写作非线性，会误导。

### 后端契约改造范围（第 3 轮浮现，待确认）
本次重构预计需要后端新增/修改的 SSE 事件：
- `reasoning_stream`（新）——转发模型 reasoning token
- 预估字段（新）——在 `final` 或新事件里带预估时间/字数
- 可能涉及 DeepAgent 侧的 reasoning 转发改造

### 思考流处理 / 后端范围 / 黑屏期（第 4 轮确认）

**① 思考流处理 = 默认折叠 + 摘要**
- 形态：思考流默认折叠成一行拟人化摘要（"小衍正在思考第 3 章的情节..."），用户可点击展开看原始 reasoning 流。
- 收益：默认不吵；想看的人能展开。保护"小衍"人格不被原始 CoT 的工具名/自我否定破坏。
- 待定（设计阶段）：摘要怎么生成？（a) 基于阶段状态的固定文案模板；(b) 过一道 LLM 生成。属于 HOW，需求只记"要折叠+摘要"。

**② 后端改造 = 本次一起改**
- 范围：前后端一起改，覆盖后端 SSE 契约扩展（`reasoning_stream` 事件 + 预估字段）。
- 含义：本次需求**不限于前端**，交付物含后端契约与转发层改造。设计文档需含后端改造设计。
- 待定（设计阶段）：动 executor 的 stream handler 还是 DeepAgent 内部，属于 HOW。

**③ 黑屏期 = 优雅骨架 + 微动画**
- 形态：按下发送瞬间，出现精心设计的"小衍启动"状态——拟人头像 + 呼吸灯/波纹动画 + "准备中"文案。
- **关键特性：不等后端事件，纯前端即时反馈**。按下发送的瞬间就出现。
- 比纯 Skeleton 更有温度，但不强行让小衍"说话"（避免无依据的拟人台词）。

### 人格弧线：HITL / 交付 / 历史回看（第 5 轮确认）

**① HITL 提问语气 = 中性提问**
- 形态：问题本身清晰、选项标准，开头加一句小衍的引导语。
- **反差设计原则**：提问时别啰嗦（用户要做决策，要清晰高效）；这与"交稿时要庆祝"形成互补——**该冷静时冷静，该温暖时温暖**。
- 选项标签也要去技术化（不写"选项A"，写人话）。

**② 完成交付 = 有仪式感**
- 形态：completed 时有过渡动画 + 小衍的交稿语（"写好啦，第 3 章大概 XXXX 字，你看看～"）+ 结果摘要（字数/耗时）。
- 目的：让普通写作者有**成就感**——这是整个体验的情感峰值，现在是空白。
- 失败态/停止态：保持现有"重试"能力，但语气也要拟人化（"抱歉，刚才出了点问题，要我再试一次吗？"）。

**③ 历史回看 = 只留结果，折叠过程**
- 形态：历史消息只显示最终正文 + 一个可展开的"执行过程"折叠区（点开看阶段/耗时摘要）。
- 思考流、动态文案**不重播/不持久化**（节省存储，回看清爽）。
- 含义：执行过程数据是**会话内瞬态**，不进持久层。只有最终结果 + 摘要持久化。

### 调性 / 节奏 / 记忆感（第 6 轮确认）

**① 常态语气 = 活泼陪伴**
- 执行中途的动态文案带语气词和情绪（"嗯，让我想想...""好嘞，开写啦！"）。
- 有陪伴感，像活泼的写作伙伴。

**② 小衍的完整情绪曲线（设计阶段需遵循）**
基于前几轮确认，"小衍"在不同节点有不同情绪浓度，形成一条曲线：
| 节点 | 情绪 | 浓度 |
|---|---|---|
| 黑屏期（启动） | 优雅骨架+微动画，不说话 | 冷静 |
| 执行中常态 | 活泼陪伴（语气词、情绪） | 温暖 |
| 思考流折叠摘要 | 拟人化一行 | 温暖 |
| HITL 提问 | 中性清晰（收敛活泼） | 冷静 |
| 完成交稿 | 仪式感+庆祝（放大活泼） | 峰值 |
| 失败/停止 | 拟人化歉意+鼓励重试 | 温暖 |

**③ 交付节奏 = 前后端两期**
- **P1（前端 + 编排重构）**：用现有数据能做的全部——小衍人格、黑屏期骨架、动态文案轮播、字数进度、脉动动画、思考流折叠壳（P2 来数据前用占位）、交付仪式、历史折叠、HITL 语气、记忆感、home.tsx 拆分/抽状态机。
- **P2（后端契约扩展）**：`reasoning_stream` 事件 + 预估时间/字数字段 + DeepAgent/executor 转发层改造。P1 完成后接入。
- P1 必须能独立交付可见成果（不依赖后端改造的部分先跑起来）。

**④ 多轮记忆感 = 要体现**
- 同一会话第二次发起时，小衍开场白体现记忆（"好的，接着上次的故事..."）。
- 增强连续创作的关系感。
- 待定（设计阶段）：记忆的依据是什么？（会话历史摘要？上一次产出？）属于 HOW。

### P1 编排重构力度（第 7 轮确认）

**P1 = home.tsx 深度重构（全面重写）**
- 力度：home.tsx 整个重写，状态全部入 store，按领域拆分。
- 风险等级：**高**（1826 行上帝组件，承载所有创作端逻辑）。
- 这是本次需求中风险最高的单项，设计文档需重点产出重构策略（分步迁移、回归测试覆盖、灰度方案等）。
- 约束（非方案）：重构后必须保留现有全部功能语义（会话管理、HITL、文生图流、停止/重试、积分拦截、心跳超时等），不得丢功能。

## 需求冻结声明

经 7 轮交互挖掘，所有核心决策已拍板，用户确认"可以冻结"。

### 需求基准摘要（一句话）
**把创作端 Agent 执行过程从"冷的状态报表"重做为"有温度的 AI 写作伙伴'小衍'在工作的过程"，通过信息丰富化（思考流+预估+字数+动态文案+脉动动画）解焦虑，全程去术语化拟人化，前后端两期交付，P1 含 home.tsx 深度重构。**

### 17 个已确认关注面
1. 核心理念：焦虑/术语/断裂（非不透明）
2. 目标用户：普通写作者
3. Agent 人格：叫"小衍"，第一人称
4. 焦虑解法：信息丰富化
5. 思考流：真 reasoning，默认折叠+摘要
6. 预估时间：后端推
7. 进度表达：字数+动态文案+脉动（不要阶段条）
8. 黑屏期：优雅骨架+微动画，即时反馈
9. 常态语气：活泼陪伴
10. HITL 语气：中性
11. 交付仪式：有仪式感
12. 历史回看：只留结果，折叠过程
13. 改造范围：最大档
14. 后端改造：本次一起改
15. 交付节奏：前后端两期
16. 多轮记忆：要体现
17. P1 编排重构：home.tsx 深度重构（高风险）

### 明确不做的事（边界）
- ❌ 不往"给用户看更多 raw 信息/trace 细节"走（不是痛点）
- ❌ 不做阶段进度条（Step 1/5，写作非线性会误导）
- ❌ 思考流不默认展开原始 CoT（折叠+摘要）
- ❌ 历史消息不持久化思考流（只留结果+摘要折叠）
- ❌ 黑屏期不让小衍无依据说话（只骨架+动画）

### 留给设计阶段的开放项（非需求模糊点）
- 各阶段的具体重命名文案
- 停止/失败的人话文案模板
- 思考流摘要的生成方式（模板 vs LLM）
- home.tsx 重构的具体拆分策略
- 记忆感的实现依据
- 后端 reasoning 转发的具体改法（DeepAgent vs executor 契约层）
