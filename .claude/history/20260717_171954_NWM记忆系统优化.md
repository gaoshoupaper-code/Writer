# NWM 记忆系统优化需求

## 核心诉求

基于 NWM 论文（Narrative World Model）优化 Writer 现有记忆系统（已落地 Graphiti + FalkorDB + 四阶段检索骨架 + harness 可进化），针对 5 个具体方向对齐论文精髓、补齐当前实现 gap：
1. 章节进入记忆的时机（Causal Publish Flow 的"定稿"概念）
2. 检索方法与查询条件（四阶段 + 叙事学 query 分类）
3. 哪些要素作为 harness 进化对象（抽取 prompt/schema/middleware 的进化优先级）
4. 检索记录如何写入 trace（evidence-backed + support trace）
5. 创作客户端如何观测当前世界状态（从黑盒到可观测）

## 现状对照（论文 vs 现有代码/设计）

| 维度 | 现状（代码已落地） | 论文精髓（gap） |
|------|------------------|----------------|
| 入图时机 | storybuilding/writing 子代理 task 完成即异步入图（边写边入） | Causal Publish Flow：每章**定稿后**才发布；改旧章节要 invalidate 下游 |
| 检索查询 | `_build_query` 仅 `task[:2000]`；**causal_cutoff 未传**（已知 bug） | 四阶段全落地 + 叙事学 query 分类（6 类） |
| 可进化要素 | middleware/schema/parser/calendar/prompts 已在 harness | 抽取 prompt 是进化核心；type label 非银弹（消融3），schema 进化方向需校准 |
| trace 记录 | TraceMemoryQuality 仅 6 字段（token/count/ok/error） | evidence-backed：每节点带 source_chapter/evidence_span + support trace |
| 客户端观测 | 完全黑盒，无 API 暴露图谱 | registry 的"当前世界状态切片" + RLM QA support trace 可暴露给作者 |

## 已确认决策（R1+R2）

| # | 决策点 | 选择 | 含义 |
|---|-------|------|------|
| D1 | 章节进入记忆的时机 | **B. 整个写作 pipeline 完成才定稿** | 入图钩子现状 `_on_writing_chapter_done`（events.py:343）已挂在 writing subagent（含内部 review-revise）返回后，**语义已对齐**；需补幂等去重 |
| D2 | 检索触发频率 | **B. 每章开始时一次** | 现状 `abefore_model` 已是"每章一次"（每次 task(writing)=新 graph 执行） |
| D3 | 客户端观测形态 | **A. 世界状态摘要文本** | 每章后生成「当前世界快照」markdown 供作者审计；不做图谱可视化；证据溯源面板留待未来 |
| D4 | 定稿事务保证 | **B. 加幂等去重** | 入图前查"这章入过没"，入过先 invalidate 再重抽；解决 resume 重写污染；对齐论文"编辑重发传播"机制 |
| D5 | 检索模式 | **A+C 混合**：基础包注入一次 + `recall_memory` 工具按需深挖 | abefore_model 注入精简基础包（写本章必看，~3-5k 字符）；同时挂 recall_memory(query, intent) 工具供 LLM 按场景深查；基础包兜底，工具精准 |
| D6 | 查询构造 | **B. 单 query + 结构化查询意图** | 修 causal_cutoff bug（阶段1启用）；query 文本显式带结构化提示（"截至第N章""张三的状态""哪些伏笔未回收"）引导检索；不做 6 类分类器（留 evolution 进化） |

## 关键事实澄清（R2 探索发现）

- **Writer 无"单章 pipeline"概念**：整本书在一次 `generate_stream` 里由 meta-agent LLM 自主循环驱动；review-revise 封装在 writing subagent 内部；meta 只看摘要
- **章节号无持久化字段**：从 task description 正则提取，executor 侧（events.py:71）和 harness 侧（memory_recall_middleware.py:237）有**两份独立实现**，改正则要同步两处
- **已知 bug**：`memory_recall_middleware.py` 调 `backend.retrieve` 时未传 `causal_cutoff`——NWM 四阶段阶段1 实际未启用
- **`MemoryUnavailableError` 定义了但没用**：middleware 抛的是裸 RuntimeError

## 已确认决策（R3）

| # | 决策点 | 选择 | 含义 |
|---|-------|------|------|
| D3-form | 世界状态展示形态 | **B. 独立 API + 前端 panel（文本渲染）** | 从 FalkorDB 查询产物组装成"截至第N章世界状态"结构化文本；**不展示原始图谱**（避免标签误导、置信度陷阱、颗粒度错位）；不做关系图缩略 |
| D7a | 摘要触发时机 | **A. 每章入图后自动生成** | 章节定稿入图后顺带生成世界状态切片；作者无需操作 |
| D7b | 摘要输出渠道 | **B. 独立 API + 前端 panel** | `GET /api/workspaces/{id}/world-state?chapter=N`；前端纯文本 panel（可按章号查询历史状态） |
| D7c | 摘要颗粒度 | **B. 详尽版** | 每个主要角色的完整状态切片 + 所有关系现状 + 所有 open promise + 世界规则（registry 完整投影） |
| D8 | 可进化要素优先级 | **C→A→B 顺序**：schema → 抽取 prompt → 检索 middleware | 符合论文消融逻辑链（定义能记什么 → 决定记对没 → 决定用上没）；parser/calendar 低优 |
| D9 | trace 颗粒度 | **B. 加召回节点清单** | TraceMemoryQuality 扩展：每个召回节点带 name/type/source_chapter（不带原文 evidence_span）；evolution 能定位"召回了什么/漏了哪类"；体积可控 |

## 已确认决策（R4 收尾）

| # | 决策点 | 选择 | 含义 |
|---|-------|------|------|
| D10 | 预算分配（C 方案） | 基础包 **12k 字符** + 工具单次 **2k 字符/次** + 工具次数 **不限** + **章节总上限 20k 字符（硬截断安全阀）** | 用户偏好放开召回灵活性；20k 硬截断防 token 爆炸。**已知风险**：偏离论文 12k 最优预算，长篇后期可能触发 lost-in-the-middle；evolution 需在 20k 内优化召回策略 |
| D11 | 摘要生成方式 | **B. 入图时缓存快照**（不消耗 LLM，纯结构化投影） | 每章入图后顺带生成快照存盘；API 只读快照；图查询结果直接拼 markdown 表格（非叙述化散文）；成本≈一次图查询；章节未入图时查不到 |
| D12 | 详尽版角色范围 | **D. 全部角色但分主次** | 主角+重要配角（有 BELONGS_TO_THREAD 或参与过 StoryNode）给完整状态切片（位置/知识/关系/伏笔）；路人 NPC 仅列一行（姓名+身份+最后出场章号） |

## 关键设计哲学（贯穿所有决策）

- **图谱对作者是黑盒**：作者看到的是"图的查询产物"（叙事语言组织的视图），不是图谱本身（Character/RELATIONSHIP/valid_at 等工程标签）
- **叠加而非替换**：markdown 文件仍是人读真相源；Graphiti 图谱是机读记忆层；两者职责不同不互相取代
- **可进化优先**：记忆系统作为 harness 要素接入现有 evolution 闭环，不新建机制；schema/prompt/middleware 顺序开放进化

### 关键设计哲学（贯穿所有决策）

1. **图谱对作者是黑盒**：作者看到的是"图的查询产物"（叙事语言组织的视图），不是图谱本身（Character/RELATIONSHIP/valid_at 等工程标签）。理由：论文消融3 证明 type label 非银弹；作者看原始图会掉进分类学陷阱/置信度陷阱/颗粒度错位
2. **叠加而非替换**：markdown 文件仍是人读真相源；Graphiti 图谱是机读记忆层；两者职责不同不互相取代
3. **可进化优先**：记忆系统作为 harness 要素接入现有 evolution 闭环，不新建机制；schema/prompt/middleware 顺序开放进化
4. **有界预算是核心机制（已妥协）**：论文 12k 最优预算被用户放宽到 20k（基础包 12k + 工具不限），20k 硬截断作安全阀；evolution 需在 20k 内优化召回策略补回偏离的机制优势

### 已知 bug（本次需顺手修）

1. **causal_cutoff 未传**：`memory_recall_middleware.py` 调 `backend.retrieve` 时未传 causal_cutoff 参数 → NWM 四阶段阶段1 实际未启用
2. **MemoryUnavailableError 定义未用**：`errors.py` 定义了专用异常，但 middleware 抛的是裸 RuntimeError → API 层无法精确捕获
3. **章节号正则两份独立实现**：`events.py:71` 和 `memory_recall_middleware.py:237` 各有一份（harness 不能 import executor）→ 改正则要同步两处

### 落地范围（补齐 vs 重构）

**补齐现有 Graphiti 路径，不重构**：
- executor 侧：修 bug + 加幂等去重 + 加缓存快照生成 + 加 world-state API
- harness 侧：改 `_build_query`（结构化意图）+ 传 causal_cutoff + 加 recall_memory 工具 + 调整基础包排版
- contracts 侧：扩展 TraceMemoryQuality（加召回节点清单字段）
- 前端：新增 world-state panel 组件
- evolution 侧：开放 schema/prompt/middleware 进化（已有 edit_source 工具，无需新建）

### 未解决问题（留给设计/开发阶段，不阻塞需求冻结）

1. recall_memory 工具的 intent 参数枚举值（latest_state / knowledge_boundary / promise_payoff / relationship / object_location / temporal_order）——论文 6 类是否全要，还是先开 3 类
2. 缓存快照的存储位置（workspace 文件 vs evolution.db vs 独立表）
3. 主次角色判定的"重要配角"阈值（BELONGS_TO_THREAD 是否够，还是要加权）
4. evolution 如何观测"召回 token 是否撞 20k 上限"并据此优化
