# 设计：NWM 记忆系统重构

> 需求基准见 `20260717_192618_NWM记忆系统重构.md`（D-R1~R6，已 confirmed）。
> 本设计解决 HOW：技术选型、架构分层、接口契约、数据模型、任务拆解。

## 架构方向（待用户确认）

把现状"Graphiti 薄封装"替换为"NWM 原生实现"：
- 存储：SQLite（typed records 关系表）+ sqlite-vec（向量）+ FTS5（BM25）
- 检索：四阶段自研（causal cutoff + hybrid RRF + SQL JOIN one-hop + bounded packet）
- 抽取：单次 LLM 调用（json_object 降级 + schema hint，复用 client.py 降级逻辑）
- 分层：executor 固定 DB 原语 + harness 可进化业务逻辑

---

## 设计阶段发现的技术断层（需求未覆盖，HOW 绕不开）

调研中发现 5 个需求阶段没触及、但设计必须先拍板的技术断层：

1. **[断层1] embedding 生成方式**：sqlite-vec 只存查向量，**生成**向量要 embedding 模型。
   executor 现无 embedding 客户端（之前靠 Graphiti 内部 OpenAIEmbedder 调智谱 embedding-3）。
   根目录有 `bge-small-zh-v1.5`（367M，512维，中文优化，已备好未接入）。
2. **[断层2] sqlite-vec 部署形态**：是 SQLite 扩展（.dll/.so），Docker 镜像默认不带，要安装。
3. **[断层3] LLM structured output 方式**：DeepSeek/GLM 不支持 json_schema，executor 也无先例。
   client.py:128-196 有 `json_object` 降级 + schema hint 现成逻辑，复用还是重写？
4. **[断层4] memory.db 的放置与生命周期**：一作品一文件，文件放 workspace 下还是统一目录？
   连接管理（per-request？池化？进程单例？）。
5. **[断层5] 新增 executor 原语模块的组织**：DB 原语（store/fts/vec/join/extract）放哪个模块？
   替换掉 `memory/backend.py + client.py + ingestion.py` 三件套，新的模块边界怎么划。

## 已确认设计决策（R1 — 存储与 embedding 基建）

- **D-D1-1 embedding 生成**：智谱 embedding-3 在线 API（2048 维）。
  - **明确接受外部 API 依赖**：断网/key 失效 → 记忆系统整体降级全量注入（与 D-R5-1 失败语义一致）。
  - 复用现状 `MEMORY_EMBED_API_KEY` / `MEMORY_EMBED_BASE_URL` / `MEMORY_EMBED_MODEL` 配置。
  - 根目录 `bge-small-zh-v1.5` 暂不接入（保留作为未来离线方案备选）。
- **D-D1-2 sqlite-vec 部署**：`pip install sqlite-vec + pysqlite3-binary`。
  - 启动时 `__import__('pysqlite3'); sys.modules['sqlite3']=sys.modules['pysqlite3']` 替换标准库。
  - Dockerfile 加两个 pip 依赖，无需编译，镜像增约 10MB。
- **D-D1-3 record embed 内容**：语义拼接。
  - 把 record 关键语义字段拼成自然语言文本再 embed（如 CharacterState → "角色：林晚。目标：复仇。知道：玉佩秘密..."）。
  - 拼接模板归 harness 可进化（属 packet_formatter/schema 边界，D-R1-2）。
  - 检索时 query 也 embed，做语义匹配。
  - sqlite-vec 表维度：`vec0(embedding float[2048])`。

## 已确认设计决策（R2 — 模块边界与生命周期）

- **D-D2-1 模块拆分**：`executor/app/platform/memory/` 下按职责拆 5 模块，保留 MemoryBackend 门面：
  - `store.py` — SQLite 连接管理 + DDL + CRUD（最底层，纯存取）
  - `embedder.py` — 智谱 embedding-3 客户端封装
  - `extractor.py` — LLM 抽取（json_object 降级 + schema hint，从 client.py:128-196 复用改造）
  - `retriever.py` — 四阶段检索编排（调 store + embedder）
  - `ingestion.py` — 管道入口（events.py 调用，编排 extract → embed → store）
  - `backend.py` — `MemoryBackend` 门面类（保留 `retrieve`/`health_check` 接口，对 harness 透明，内部组合上述模块）
  - `client.py` — **删除**（Graphiti 构造工厂，不再需要）
- **D-D2-2 db 放置与连接**：
  - db 文件路径：`{DATA_DIR}/memory/{workspace_id}.db`（本地数据目录按 workspace_id 索引，不放 workspace 内因 workspace 可能是远程文件系统）。
  - 连接管理：`MemoryStorePool` LRU 缓存（照搬 `checkpoint_pool.py` 范式），max=32，一作品一连接复用。
  - WAL 模式 + `check_same_thread=False`（照搬 executor 元数据库范式）。
- **D-D2-3 抽取模型**：独立配置，不走 ctx.model。
  - 新增配置项：`MEMORY_EXTRACT_API_KEY` / `MEMORY_EXTRACT_BASE_URL` / `MEMORY_EXTRACT_MODEL`。
  - 默认 `deepseek-chat`（非思考模式）或 `glm-4.6`。
  - executor 定模型（符合 D-R6-2），harness 只改 extractor prompt。

## 已确认设计决策（R3 — 数据模型/registry 合并语义）

- **D-D3-1 registry 合并：追加 + 视图取最新**。
  - 每条 record 独立 INSERT（不覆盖旧记录），带 source_chapter / valid_at / invalid_at。
  - 检索时用 SQL 视图 + 窗口函数取"最新有效切片"：`ROW_NUMBER() OVER(PARTITION BY entity ORDER BY source_chapter DESC)`。
  - 累积类字段（knowledge）：取 cutoff 前所有记录的合集（GROUP_CONCAT 或应用层聚合）。
  - 状态类字段（status/location/goal）：取每个实体最近一条记录的值。
  - 忠实论文 §3.3 "selects the latest edge valid at n for each entity while older edges remain as history"。
- **D-D3-2 PlotPromise 状态机：唯一记录 + 状态 UPDATE**。
  - plot_promise 表：thread_id / structural_role / status(open|closed) / setup_chapter / payoff_chapter / evidence_span。
  - 第3章抽取检测到新伏笔 → INSERT（status=open）。
  - 第10章抽取检测到兑现 → UPDATE 同一 promise 的 status=closed, payoff_chapter=10。
  - 匹配逻辑：extractor 输出里标注 `updates_promise_id`（指向已存在 promise）或 `is_new`。
- **D-D3-3 题材驱动 record 启用**：
  - harness 提供 `record_type_policy.py`，题材 → record 类型映射表。
  - 抽取时按 policy 跳过禁用类型（表都在，只是不填）。
  - 未明确题材时全启用（保险，宁可多抽不漏）。

## 已确认设计决策（R4 — 接口契约）

- **D-D4-1 retrieve 签名向后兼容**：保持 `retrieve(query, group_id, budget_chars, num_results)`。
  - causal_cutoff（章节号）不进签名——改为 backend 内部从 query 或 group 上下文推断，或通过 packet 返回（供 trace）。
  - ⚠️ 待细化：causal_cutoff 怎么传给 backend？middleware 构造 cutoff 后放哪？——**方案：retrieve 新增可选 kwarg `causal_cutoff: int | None = None`**（向后兼容，旧调用不传则不过滤）。
- **D-D4-2 EvidencePacket 扩展字段（供 trace 审计）**：
  - 保留现状字段：`nodes` / `edges` / `formatted` / `token_estimate` / `query_used` / `__bool__`。
  - 新增字段：`hits: list[dict]`（命中 record 摘要：type/name/source_chapter/valid） / `causal_cutoff: int | None` / `stage1_count: int`（cutoff 后总数）/ `stage2_anchors: list[str]` / `stage3_expanded: int` / `truncated: bool`。
  - middleware 不读新字段（只读 formatted/token_estimate/nodes/edges），新字段只供 quality_callback 埋点。
- **D-D4-3 middleware 改动范围（最小）**：
  - `abefore_model` 的 except 分支：`raise RuntimeError` → `self._record_quality(...) + return None`（降级不中断）。
  - `_record_quality`：从 packet 取扩展字段填充 callback dict。
  - 构造 `causal_cutoff = chapter_num - 1 if chapter_num else None` 传入 retrieve。
  - `_build_query` / `_format_packet` 保持 harness 可进化，不改。

## 已确认设计决策（R5 — 降级兜底链）

- **D-D5-1 双 middleware 兜底链（关键修复）**：
  - `writing.py` 的 if/else 互斥改为**同时挂载** ContextAssembler + memory_recall。
  - ContextAssembler 总是挂载（兜底）；memory_recall 非 None 时追加在其后。
  - **执行顺序**：memory_recall.abefore_model 先执行 → 成功注入记忆（带前缀"记忆召回："）→ ContextAssembler 幂等检测到记忆前缀则跳过；memory_recall 失败返回 None → ContextAssembler 兜底全量注入。
  - ⚠️ 待验证：middleware 执行顺序是否按 append 顺序？DeepAgents 洋葱模型通常是后挂的先执行（类似后进先出），需在实现时确认顺序并调整挂载顺序。

## 数据模型（SQLite Schema 详设）

### 8 类 typed record 表（共享时序字段 + 各自语义字段）

所有表共享时序字段：
```sql
id INTEGER PRIMARY KEY,
workspace_id TEXT NOT NULL,
source_chapter INTEGER NOT NULL,   -- 抽取自第几章（因果锚点）
valid_at INTEGER NOT NULL,         -- 从第几章开始有效
invalid_at INTEGER,                -- 第几章被取代（NULL=仍有效）
evidence_span TEXT NOT NULL,       -- evidence-backed 原文引用
created_at TEXT DEFAULT (datetime('now'))
```

**1. chapter_digest**（章节摘要）
```sql
CREATE TABLE chapter_digest (
  -- 共享时序字段 + workspace_id/source_chapter/valid_at/invalid_at/evidence_span
  summary TEXT NOT NULL,           -- 本章事件/状态变化/场景骨架摘要
  key_events TEXT,                 -- JSON: 本章关键事件列表
  KEYWORD_INDEX TEXT               -- 用于FTS5的关键词串
);
```

**2. scene**（场景事件）
```sql
CREATE TABLE scene (
  scene_id TEXT NOT NULL,          -- 场景标识（chapter+序号）
  location TEXT,                   -- 地点
  participants TEXT NOT NULL,      -- JSON: 参与角色名列表
  event_order INTEGER,             -- 故事内顺序
  reveal_order INTEGER,            -- 揭露顺序（读者何时知道）
  summary TEXT                     -- 场景简述
);
```

**3. character_state**（角色状态，NWM 核心）
```sql
CREATE TABLE character_state (
  name TEXT NOT NULL,              -- 角色名（PARTITION BY 键）
  goal TEXT,                       -- 当前目标（替换语义）
  knowledge TEXT,                  -- 知道什么（累积语义，JSON数组）
  unknowns TEXT,                   -- 不知道什么（累积语义）
  status TEXT,                     -- 状态（替换语义：潜逃/受伤/...）
  location TEXT,                   -- 位置（替换语义）
  relationship_deltas TEXT         -- JSON: 本章关系变化
);
```

**4. relationship_state**（关系状态）
```sql
CREATE TABLE relationship_state (
  char_a TEXT NOT NULL,
  char_b TEXT NOT NULL,
  relation_type TEXT,              -- 师徒/宿敌/盟友（替换语义）
  polarity TEXT,                   -- 正面/负面/中性/矛盾（替换语义）
  relationship_desc TEXT           -- 关系简述
);
```

**5. object_state**（关键物品，视题材启用）
```sql
CREATE TABLE object_state (
  name TEXT NOT NULL,
  owner TEXT,                      -- 持有者（替换语义）
  location TEXT,                   -- 位置（替换语义）
  condition TEXT                   -- 状态（替换语义：完好/损坏/...）
);
```

**6. plot_promise**（伏笔承诺，论文碾压点）
```sql
CREATE TABLE plot_promise (
  promise_id TEXT NOT NULL,        -- 唯一标识（thread_id或语义ID）
  thread_id TEXT,                  -- 所属故事线
  structural_role TEXT,            -- 结构角色
  status TEXT NOT NULL,            -- open | closed（状态机）
  setup_chapter INTEGER NOT NULL,  -- 铺设章节
  payoff_chapter INTEGER,          -- 兑现章节（closed时填）
  promised_payoff TEXT,            -- 承诺的兑现内容
  resolution TEXT                  -- 实际兑现描述
);
```

**7. narrative_function**（叙事功能，论文碾压点）
```sql
CREATE TABLE narrative_function (
  scene_ref TEXT,                  -- 关联场景
  focalized_observer TEXT,         -- 视角人物（谁知）
  dramatic_beat TEXT,              -- 戏剧拍子
  turn_or_reversal TEXT,           -- 转折/反转
  reader_knowledge TEXT,           -- 读者知道什么（vs角色）
  summary TEXT
);
```

**8. world_fact**（世界设定）
```sql
CREATE TABLE world_fact (
  fact TEXT NOT NULL,
  category TEXT,                   -- 势力/技术/魔法体系/社会结构
  scope TEXT,                      -- 适用范围
  valid_chapter_range TEXT         -- 有效章节范围
);
```

### 辅助表（向量 + 全文检索）

```sql
-- 每类 record 一个向量虚拟表（sqlite-vec）
CREATE VIRTUAL TABLE character_state_vec USING vec0(
  embedding float[2048],
  record_id INTEGER
);
-- 其余 7 类同构

-- 统一全文检索（FTS5）
CREATE VIRTUAL TABLE records_fts USING fts5(
  record_type,            -- character_state/scene/...
  entity_name,            -- 实体名（角色名/场景ID/...）
  search_text,            -- 语义拼接的可检索文本（D-D1-3）
  source_chapter UNINDEXED,
  workspace_id UNINDEXED
);

-- registry 视图：取最新有效切片（论文 §3.3 核心）
CREATE VIEW current_character_state AS
SELECT * FROM (
  SELECT *,
    ROW_NUMBER() OVER(
      PARTITION BY workspace_id, name
      ORDER BY source_chapter DESC
    ) rn
  FROM character_state
  WHERE invalid_at IS NULL OR invalid_at > 0  -- 运行时填 cutoff
) WHERE rn = 1;
-- 其余替换语义表同构
```
