# 需求：harness 版本机制——去 DB、轻量化重构

## 核心诉求（待用户确认）

> **一句话**：把 harness 版本管理从「git + DB 双真相源割裂」重构为「单一清晰机制」；数据量小（几百~几千版本），不要因为"现在有 DB"就留 DB，零技术债；重构后的设计要从业界最佳实践（9系统调研结论）落地为符合本项目体量的轻量级实现。

## 背景：当前割裂的物理根因（已用数据确认）

1. **三 git 实体纠缠**：主仓库 + `current/.git`（remote 指向整个 Writer 项目）+ `harness.git`（整个项目克隆）。无 `.gitmodules`，半嵌套半克隆。
2. **DB 与 git 内容重复**：`harness_snapshots.config_json`（29270字节）把 `prompts/*.md` 正文整段重复存了一遍，同时又有 `source_commit` 指向 git。两份真相必须人工同步 → 必然 drift。
3. **DB 里 harness 相关只有 3 行**（version 1/2/3），其余 16 张表是 trace/评估/其他业务，与"harness 版本管理"无关。

## 业界调研定论（已确认，见 report.md）

- 6/9 自进化系统用代码文件做版本载体，git 是强化版；DB 载体仅 Langfuse 且证明装不下多文件 .py 包。
- 分层真相源：git 管"内容"，DB/manifest 管"谱系+状态+评分"。
- 但这是"业界最佳"——**本项目体量（几百~几千版本）是否需要这么重，待需求挖掘确认**。

## 全要素清单（待挖掘时逐一判断是否需要）

> 按用户偏好：把所有可能的要素全列出来，逐一分析。

### 版本管理的 7 个职责维度（每个都要回答"谁来做"）
| # | 职责 | 当前在哪做 | 业界怎么做 | 待定 |
|---|------|-----------|-----------|------|
| A | **版本内容存储**（prompts/middleware/skills 源码） | git + DB config_json 重复 | git only | |
| B | **版本谱系**（parent_version 链） | DB harness_snapshots.parent_version | DB 或 manifest 文件 | |
| C | **部署状态**（哪个 version 当前是 production） | DB status 字段 | DB label 或 git ref | |
| D | **内容去重**（tree hash 防爆炸） | 无 | DB 存 tree_hash 或 git 天然 | |
| E | **评估分数/门控**（每版本几分、过没过） | DB version_changes/evolve_sessions | DB 或 manifest | |
| F | **变更日志**（每版本改了啥） | DB version_changes.diff_json | commit message 或 manifest | |
| G | **审计/谱系查询**（列出所有版本、谁拉的、何时回滚） | DB | DB 或 git log | |

### 三个候选方案（待权衡）
1. **纯 git + manifest 文件**（最轻）：版本内容、谱系、状态全在 git，DB 完全不碰 harness
2. **git 内容 + 极简 DB 元数据**（中轻）：git 管内容，DB 只存少量索引（version/commit/score/status）
3. **维持现状优化**（重）：保留 DB 但去重，去掉 config_json 重复

## 已确认决策（D1 轮）

- ✅ **范围**：只针对 harness 版本管理。trace/评估/会话等可观测数据保留在 evolution.db（它们适合 DB）。
- ✅ **元信息载体 = manifest 文件**（最轻方案）。不引入新 DB。harness 版本管理的版本列表/谱系/production 指针/评分，用一个 manifest 文件存。
- ✅ **版本内容真相源 = git 唯一**。彻底去掉 DB 的 config_json 重复内容。
- ✅ evolution.db 保留（管 trace/评估/会话），但砍掉 `harness_snapshots` 和 `version_changes` 两张与版本强绑定的表 → 职责收窄为"只管可观测数据"。

## 七个职责维度的归属（基于 D1 决策更新）

| # | 职责 | 归属（D1 后） |
|---|------|--------------|
| A | 版本内容存储 | git（唯一） |
| B | 版本谱系 parent 链 | manifest 文件 |
| C | 部署状态 production 指针 | manifest 文件 |
| D | 内容去重 tree hash | git 天然 tree hash |
| E | 评估分数/门控 | manifest 文件 |
| F | 变更日志 | git commit message + manifest |
| G | 审计/谱系查询 | git log + manifest |

## 已确认决策（D2 轮）

- ✅ **回滚触发者 = 只进化端（单向流）**。executor 纯只读，无写 production 指针能力。一致性设计大幅简化。
- ✅ **executor 已不连 DB 读 production**——`git_sync.py` 的 `pull_production()` 直接 `git reset --hard origin/main`，production = bare repo 的 main 分支。
- ✅ **数据铁证三套真相源脱节**：DB production=b8a171d(v3)，harness.git/current main=bc70058，完全不一致。

## executor 读 production 的真实机制（代码级确认）

```
executor/git_sync.py pull_production():
  fetch origin → reset --hard origin/main    ← production = main 分支 HEAD
executor/loader.py load_current_package():
  pull_production() → load_package(checkout) → pkg.assemble(ctx)
```
- executor **不连 evolution.db**。
- production 指针现在已经是「bare repo 的 main 分支」——只是 DB 里还冗余存了一份 status='production'。
- 这意味着「去 DB」对 executor **零影响**——它本来就不读 DB 的 production。

## 当前割裂的完整画像（代码+数据铁证）

1. **无独立 harness 仓库**：`harness.git` 和 `current/.git` 都是整个 Writer 项目的克隆，log 全是 refactor evolution/feat desktop 等无关 commit。
2. **DB 与 git 脱节**：DB production=v3(b8a171d)，git main=bc70058，谁都不认谁。
3. **config_json 重复**：DB 把 prompts/*.md 正文整段重复存（29270字节），磁盘又有一份。

## 已确认决策（D3 轮）

- ✅ **manifest 进 git（版本注册表）**。production 指针 = main 分支（executor 已 pull main，零额外机制）。manifest 只记录 git branch 管不了的：版本谱系（每版本 commit/评分/parent）+ 回滚历史日志。
- ✅ **harness 完全独立成自己的 git 仓库**。主仓库 Writer 通过 `.gitignore` 完全不碰 harness 内容，代码里只有"读 harness 的路径"没有 harness 内容本身。彻底解耦，消除三套真相源。

## 重构骨架（基于 D1-D3）

```
独立 harness 仓库（完全独立，主仓库 .gitignore 掉）
harnesses-repo/                        ← 它自己的 git 仓库
├── prompts/ middleware/ skills/ subagents/ tools/   ← harness 源码内容
├── __init__.py                        ← assemble(ctx) 入口
└── registry.json                      ← 版本注册表（谱系/评分/回滚日志）

主仓库 Writer/
└── （不跟踪 harnesses-repo，.gitignore 掉）
    └── evolution 端通过路径操作 harnesses-repo（写）；executor pull bare repo（读）
```

- production = harnesses-repo 的 main 分支
- 版本 = main 上的 commit
- 回滚 = evolution 把 main 重置/合并回某个旧 commit（或用标签）
- executor `pull main` = 拿到 production（现有机制不变）
- manifest(registry.json) 随内容在同一 commit，executor pull 一次拿全

## 已确认决策（D4 轮）

- ✅ **回滚 = git revert（线性前进）**。main 分支始终前进，所有版本（好坏）都在 main 线性历史上可查，谱系最完整。坏版本不被擦除，符合自进化系统"谱系完整性 > 前进纯净性"共识。
- ✅ **评估分数/门控状态进 registry.json**。每版本一条：version/commit/parent_version/eval_score/eval_status/created_at/change_summary。随版本走，查询"v3 多少分"直接读 registry，无需 JOIN。
- ✅ **版本编号 = 递增整数**（v1/v2/v3）。revert 不产生新版本号（回滚是 main 的 revert commit，不是新 harness 版本）；registry.json 记录回滚日志（何时、从哪回退到哪、原因）。

## 七个职责维度的最终归属（D1-D4 全部确认）

| # | 职责 | 归属 |
|---|------|------|
| A | 版本内容存储 | git（独立 harness 仓库，唯一真相源） |
| B | 版本谱系 parent 链 | registry.json（version + parent_version + commit） |
| C | 部署状态 production | main 分支（executor pull main） |
| D | 内容去重 | git tree hash 天然（同 tree 不重复提交） |
| E | 评估分数/门控 | registry.json（eval_score + eval_status） |
| F | 变更日志 | git commit message + registry.json change_summary |
| G | 审计/谱系查询 | git log（main 线性历史）+ registry.json |

## 已确认决策（D5 轮，收尾）

- ✅ **executor 同步 = push + 周期 reconcile**。维持现有 ship 后调 /reload（push 通知）+ executor 后台周期轮询 main（防通知丢失自愈）。符合 GitOps 第4原则。
- ✅ **门控 = 分阶段**。当前仅静态校验（py_compile + import，现状）；架构预留 eval 门控接入点，等 evaluation 体系成熟再插上（不加空架子=真零技术债）。
- ✅ **门控不强加的依据**：eval 体系仍在演进（evaluation_sessions 仅7行），现在加自动门控是伪需求。人工 ship 前把控质量。防作弊（DGM 教训）随 eval 门控一并后期补。

## 约束清单（设计阶段必须满足）

1. harness 完全独立 git 仓库；主仓库 .gitignore 不碰内容。
2. production = harness 仓库 main 分支；executor pull main（现有机制不变）。
3. registry.json 随版本进 git，记录：version/commit/parent_version/eval_score/eval_status/change_summary/created_at + 回滚日志。
4. 回滚 = git revert（线性前进，不擦历史）；registry 记回滚日志。
5. 版本编号 = 递增整数。
6. evolution.db 砍掉 harness_snapshots + version_changes 两表；trace/评估/会话保留。
7. executor 同步 = push(/reload) + 周期 reconcile（自愈）。
8. 门控当前仅静态校验，预留 eval 门控接入点（分阶段，eval 成熟再加）。
9. 清理三 git 实体（current/.git + harness.git + 主仓库半嵌套）——迁移方案留设计阶段。

## 不做（明确排除）

- 不引入新 DB（harness 版本管理零 DB 依赖）。
- 不用 submodule/subtree（调研打分最低，认知负担高）。
- 不用 OCI 制品（Agent 工程调研零票，开发态要 diff/merge）。
- 不保留 DB 的 config_json 重复内容（彻底去重）。
- 不在 harness 版本管理里加 trace/评估/会话数据（留 evolution.db）。
- 不现在加 eval 门控/防作弊（eval 未成熟，分阶段）。

## 约束（已明确）

- 不留技术债——不因"现有 DB"就留 DB
- 清晰分明，认知负担低
- 数据量：harness 版本几百~几千级别
- 要符合本项目体量（轻量级），不照搬大厂重方案
