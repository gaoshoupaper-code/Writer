# Trace 监测系统移植到进化桌面端

## 核心诉求

将 trace 监测系统的**前端可视化能力**从 evolution web 端（`evolution/frontend/`）完整移植到 evolution 桌面端（`evolution/desktop/src/`），使桌面端拥有与 web 端同等的 trace 详情可视化体验。

**背景**：trace 后端（API）早已完整迁移到 evolution（`evolution/app/trace/`、`view/traces.py`、`active.py`、`stats.py`），监测大盘（`monitor.tsx`）也已有基础实现。唯独 **trace 详情可视化层是"毛坯状态"**——当前 `trace-detail.tsx` 仅 156 行，只有平铺节点列表（仅取 depth 0/1）和平铺事件流，缺少调用链树、时间轴、抽屉、token 分析、投影逻辑等核心可视化能力。

## 现状差距矩阵（已确认）

| 能力 | web 端 (`evolution/frontend`) | 桌面端 (`evolution/desktop/src`) | 差距 |
|------|------|------|------|
| Trace 详情页 | ✅ `/traces` 完整 | ⚠️ `trace-detail.tsx` 极简（156行） | 需重写 |
| 调用链时间轴 | ✅ `TraceChainTimeline.tsx` (16KB) | ❌ 无 | 需移植 |
| 调用链抽屉 | ✅ `TraceChainDrawer.tsx` (13KB) | ❌ 无 | 需移植 |
| Token 用量图表 | ✅ `TokenChartPanel.tsx` (25KB) | ❌ 无 | 需移植 |
| 节点类型图标 | ✅ `ChainNodeIcon.tsx` (4.7KB) | ❌ 无 | 需移植 |
| Trace 投影逻辑 | ✅ `lib/trace.ts` (793行) | ❌ 无 | 需移植 |

| Trace 类型定义 | ✅ `lib/types.ts` | ❌ 无独立 types.ts | 需移植 |

## 技术约束（已从代码确认）

- **技术栈几乎相同**：两端均用 React 19 + radix-ui + tailwindcss 4 + class-variance-authority，桌面端额外有 react-router-dom 7。
- **API 客户端差异**：web 端用 `@/lib/monitor-api` 直连；桌面端用 `evoFetch`（Rust 中继 + `/evolution-api` 前缀）。组件移植后，API 调用层需要适配。
- **SSE 机制差异**：web 端用浏览器原生 `EventSource`；桌面端 WebView 内走 Rust `stream_request` 命令中继（已有 `evoSseStream`），不能直接用 `EventSource`。
- **路由差异**：web 端 Next.js App Router；桌面端 React Router（HashRouter），trace 详情已挂在 `/traces/:traceId`。
- **无状态管理库**：桌面端 package.json 没有 zustand，而 web 端也不依赖 zustand（用 hook 管理状态），这一点不构成障碍。

## 已确认决策

- **D1：移植范围 = 全部**——含 TokenChartPanel（25KB）及其双向跳转（图↔链路联动）。
- **D2：交互形态 = 独立页面**——重写 `trace-detail.tsx`（保留 `/traces/:traceId` 路由 + monitor 下钻），不做成嵌入式 TracePanel。
- **D3：实时能力 = 完整移植**——db 快照打底 + SSE 实时增量投影（节点树实时增长）。
- **D4：SSE 适配 = 新建 `evoTraceStream` 专用封装**——不动 `evoSseStream`，为 trace SSE 单独写支持命名事件（snapshot/end/error/data）的 generator。
- **D5：trace-detail.tsx = 完全重写**——丢弃现有 156 行毛坯代码，从 web 端链路视图逻辑出发重写。
- **D6：TokenChartPanel 双向跳转 = tab 切换**——页面内 Tabs（"调用链" / "Token 图表"），通过 state 传递 highlightedNodeId/highlightedLoopIndex 实现跨 tab 跳转。
- **D7：监测大盘新增双 Tab = "创作监测" / "进化监测"**——加在 monitor.tsx 顶部。创作 = `user_generation`；进化 = `evolution_eval` + `evolution_evolve` 合并，内部用 PurposeBadge 区分。
- **D8：监测大盘 Tab 范围 = 只影响活跃 run 列表**——统计概览/skill 统计/失败模式保持全局（不按 tab 过滤），只有活跃 run 列表按 tab 来源过滤。后端零改动。

## 深入技术约束（第二轮补充）

### 依赖链完整性

移植涉及的文件和它们的依赖关系：

```
trace-detail.tsx（重写，宿主页面）
 ├── hooks/useTraceStream.ts（移植）
 │    ├── lib/monitor-api.ts → 适配为桌面端 evoFetch（已有 getTraceDetail/getActiveRuns）
 │    └── lib/trace.ts → appendLiveTraceEvent（移植，793行投影逻辑）
 ├── components/trace/TracePanel.tsx（不复用，但拆出其子视图逻辑）
 ├── components/trace/TraceChainTimeline.tsx（移植）
 ├── components/trace/TraceChainDrawer.tsx（移植）
 ├── components/trace/TokenChartPanel.tsx（移植）
 ├── components/trace/ChainNodeIcon.tsx（移植）
 └── lib/types.ts（移植 trace 相关类型）
```

### CSS 样式差距

- web 端 globals.css trace 样式：108 行（chain-* / node-* / drawer / token-chart 等）
- 桌面端 globals.css trace 样式：299 行（但大部分是旧版 `.trace-panel` / `.trace-run-list` / `.trace-node-tree` 样式，给当前毛坯用的）
- **关键**：chain-node-row / trace-chain-layout / trace-chain-drawer / token-chart-panel 等 web 端样式，桌面端**完全没有**，需要一并移植。

### UI 基础组件

两端共用 radix-ui 同套组件。trace 组件依赖的 ui 组件（Badge/Button/Skeleton/DropdownMenu）桌面端**全部已有**，不构成障碍。

### SSE 适配点（最复杂的适配）

web 端 `useTraceStream` 用浏览器原生 `EventSource`（支持 `event:` 名分类：snapshot/end/error/data）。
桌面端 `evoSseStream` 是 async generator，**只解析 `data:` 行，不处理 `event:` 名分类**（evolve/eval SSE 只有 data 帧）。
**冲突**：trace SSE 有 `snapshot`/`end`/`error` 等**命名事件**，`evoSseStream` 当前实现会丢弃 `event:` 名，把它们全当 data 帧解析。

→ 需要增强 `evoSseStream`（或新建一个 trace 专用流封装）来支持 `event:` 名解析，否则 SSE 终态判断（end/error）和 snapshot 校准都无法工作。

### 类型定义差异

web 端有 `lib/types.ts`（完整 trace 类型）。
桌面端没有 `lib/types.ts`，trace 相关类型内联在 `api.ts` 的 `TraceDetail`/`TraceListItem` 中（结构不完全一致）。
→ 需要创建桌面端 `lib/types.ts`，移植 web 端的完整 trace 类型，并统一 `api.ts` 里的类型引用。

## 监测大盘改造需求（D7/D8 补充）

monitor.tsx 当前问题：活跃 run 列表不区分来源，看不到"创作端在跑什么"vs"进化端在跑什么"。

改造后：
- 顶部 Tabs：「创作监测」（`user_generation`）/「进化监测」（`evolution_eval` + `evolution_evolve`）
- 切 tab 时：活跃 run 列表按 `run_purpose` 过滤（前端过滤即可，后端 `getActiveRuns` 返回全量，前端按 tab 筛）
- 每条 run 加 `PurposeBadge`（进化端内部区分评估/进化）
- 统计概览/skill 统计/失败模式：保持全局不变
- 点 run 下钻 → trace 详情页（路由不变）

## ⚠️ 后端改动（D9 已确认接受）

**问题**：D7 要求活跃 run 列表按来源 tab 过滤，但后端 `/active-runs` 端点有数据缺口。

**改动方案**（active.py `active_runs_api()` 一个函数内）：
1. join runs 表时补取 `run_purpose`（runs 表已有该列，SQL 加一个字段即可）
2. 合并 `app.state.trace_recorder.list_active_runs()` 的结果（evolution 自己的活跃 trace，已带 `run_purpose`）
