# Trace 历史观测功能 设计方案

## 架构方向（Step 0 初稿，待确认）

### 全局定位

在进化端桌面新增独立"Trace 历史"页面，复用现有 trace 查询后端 + trace-detail 详情页。后端需补三块能力：时间范围过滤、用户名映射、列表分页元数据。

### 系统位置

```
evolution 后端                          桌面端
┌──────────────────────────┐           ┌─────────────────────────┐
│ view/traces.py           │           │ pages/history.tsx (新增) │
│   GET /api/traces        │◄──────────│   双 Tab + 列表 + 分页   │
│   + since/until (补)     │           │   + 时间范围 + 用户筛选  │
│   + node_count (补)      │           └────────┬────────────────┘
│   + total count (补)     │                    │ navigate
│                          │           ┌────────▼────────────────┐
│ user_sync (新增)         │           │ pages/trace-detail.tsx  │
│   定时拉 executor 用户   │           │   (复用，改返回逻辑)     │
│   写 local user 缓存表   │           └─────────────────────────┘
│                          │
│ executor /internal/users │
│   (executor 新增无鉴权)  │
└──────────────────────────┘
```

## 已确认决策

### D-设计1：用户映射链路（F1 解决方案）✅

**完整同步链路：**
```
executor /internal/users (新增，无鉴权，内网信任域)
  → evolution user_sync 任务 (定时拉取)
  → evolution.db user_cache 表 (本地缓存)
  → GET /api/traces LEFT JOIN user_cache (查询时映射)
  → 前端 TraceListItem.owner_username (直接显示)
```

**三段细节：**

**① executor 端：新增 `GET /internal/users`**
- 位置：`executor/app/routers/internal.py`（与现有 `/internal/traces` 同级）
- 无鉴权，内网信任域（与现有 internal 端点一致）
- 返回最小集：`[{ user_id, username, disabled }]`
- 实现用 `UserRepository.list_all()` 但**显式列字段**，过滤掉 password_hash / encrypted_api_key 等敏感列

**② evolution 端：新增 `user_cache` 表 + 同步任务**
- 表结构：`CREATE TABLE user_cache (user_id TEXT PK, username TEXT, disabled INTEGER DEFAULT 0, synced_at TEXT NOT NULL)`
- 迁移函数：`_migrate_user_cache(conn)`，照抄现有 `_migrate_runs_*` 模式（PRAGMA 探测 + CREATE IF NOT EXISTS）
- 同步任务：`start_user_sync_scheduler()`，照抄 scan.py 的 `asyncio.create_task + to_thread` 模式
  - 启动时跑一次 + 定时刷新（每天一次，与需求 D13 一致）
  - 同步策略：全量覆盖（DELETE + INSERT，或 UPSERT）
- 挂载位置：`main.py` lifespan，在 `start_judge_scheduler()` 后加一行

**③ evolution 端：`GET /api/traces` LEFT JOIN**
- `traces.py` 的 `list_traces` SQL 改为：
  `SELECT r.*, uc.username AS owner_username FROM runs r LEFT JOIN user_cache uc ON r.owner_user_id = uc.user_id ...`
- `TraceListItem` 加字段：`owner_username: str | None`
- 进化端 trace（owner='unknown'）JOIN 不到 → `owner_username = None` → 前端降级显示"系统"

### D-设计2：列表规模列只用 event_count（F2）✅
- 列表"规模"列只展示 `event_count`，不查 nodes 表、不新增 node_count。
- 理由：小数据量下 event_count 已能反映 trace 规模，避免子查询或冗余列的额外改动。

### D-设计3：分页响应改结构 { items, total, limit, offset }（F3）✅
- `GET /api/traces` 返回结构从 `list[TraceListItem]` 改为：
  ```python
  class TraceListResponse(BaseModel):
      items: list[TraceListItem]
      total: int        # 满足当前过滤条件的总条数
      limit: int
      offset: int
  ```
- 后端实现：额外跑一次 `SELECT COUNT(*) FROM runs r {where_sql}`（复用同一 where 拼装），和 items 查询共用过滤参数。
- **兼容性处理**：`evaluation.tsx` 调用 `getTraces` 的地方同步适配（`data.items ?? data`），属于本功能改动范围。

### D-设计4：trace-detail 返回改用 navigate(-1)（F4）✅
- trace-detail.tsx 三处 `navigate("/")` 改为 `navigate(-1)`。
- 从哪进来回哪去：历史页进→回历史页，monitor 进→回 monitor。

---

### D-设计5：user_sync 全量覆盖策略（F1 细节）✅
- 同步策略：`with _lock:` 包住 DELETE + 批量 INSERT，原子操作全量覆盖。
- 数据量小（<100 用户），保证一致性，不留孤儿残留。
- 同步频率：启动时跑一次 + 每天定时刷新（与需求 D13 一致）。

### D-设计6：executor /internal/users 无鉴权（F1 细节）✅
- 与现有 `/internal/traces` 同级，不校验 token。
- 安全边界靠 Docker 内网隔离，保持 internal 路由统一约定。

### D-设计7：时间范围过滤用 ISO 8601 时间戳（F5）✅
- 前端预设按钮（今天/7天/30天）在客户端算成 ISO 时间戳传后端。
- 后端参数：`since: str | None`、`until: str | None`。
- 过滤逻辑：`WHERE started_at >= ? AND started_at <= ?`（纯字符串比较，ISO 格式天然有序）。
- "全部"预设 = 不传 since/until，后端不加时间过滤。
- 注意：`started_at` 可能为 NULL（未收尾 trace），时间过滤天然排除 NULL（NULL 不匹配 >= / <=）。

---

### D-设计8：用户下拉数据来源 —— GET /api/users/cache ✅
- 新增 `evolution/app/view/users.py`，提供 `GET /api/users/cache` 返回 user_cache 全量。
- 返回格式：`[{ user_id, username }]`（只够下拉用，不带 disabled/synced_at）。
- 前端 history.tsx 创作历史 Tab 加载时调此接口填充用户下拉。
