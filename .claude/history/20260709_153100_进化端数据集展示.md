# 进化端数据集展示功能

## 核心诉求

在进化端桌面端（`evolution/desktop/`）新增「数据集」功能页面，把系统现有的两套评估集数据**全部展示出来**：

- **golden（冻结基准层）**：跨版本 benchmark 用的公制尺
- **growing（增长探索层）**：生产 promote 进来的真实 case

后端 API（`/api/dataset/*`、`/api/promote/*`）已完整就绪，当前缺口在桌面端前端：无导航项、无页面、API 客户端未封装。本需求即补齐这个前端缺口。

> 注：当前两层数据集可能都还没有内容（golden 仅预置 1 个 case-001，growing 可能为空），所以展示层需考虑「空状态」。

---

## 已确认决策

### D1. 功能边界：完整数据闭环（C 方案）✅
不只是只读展示，而是覆盖数据闭环的「入口 + 展示 + 出口」三段：
- **入口**：promote 标注队列（`/api/promote/tasks`）—— 生产 trace → judge 打分 → 人工 accept/reject
- **展示**：golden + growing 的 case 列表与详情
- **出口**：growing → golden 升级（`POST /api/dataset/cases/{id}/promote`，维护者独占）

### D2. 页面组织：两个 Tab（Golden | Growing）✅
顶部 Tab 切换，同一页面内分别呈现两层数据。golden 的「冻结/基准」语义与 growing 的「探索/增长」语义通过 Tab 明确对比。

### D3. 使用场景与交付标准：开发者自用分析 ✅
- 受众：开发者本人（开发/分析用途），非最终用户、非对外展示
- 含义：UI 无需过度打磨（空状态文案、引导、动效可从简）；但需要「看全面」——信息密度优先于美观，字段要全、数据闭环要清晰可追溯
- 权限：当前桌面端 Shell 有登录守卫但角色区分不明确（待澄清，见 Q-权限）

---

### D4. 页面结构：三个 Tab（Golden | Growing | 待标注）✅
- **Golden Tab**：冻结基准层 case 列表 + 详情 + 关联 benchmark（待澄清是否做）
- **Growing Tab**：已入库的探索集 case 列表 + 详情
- **待标注 Tab**：promote 标注队列（promote_tasks，pending/needs_confirm 状态），人工 accept/reject 的入口
- 数据闭环三段在页面上分占一 Tab：基准（Golden）→ 已入库（Growing）→ 待办（待标注）

### D5. 字段展示拆分 ✅
- **Case 列表（表格列）**：case_id、title、layer、demand_revision（golden 关键指纹）、source_trace_id（来源可追溯）、has_reference、promoted_at
- **Case 详情（点进去）**：demand.md 全文、reference.md 全文（如有）、created_by、status、关联 benchmark 历史

### D6. 权限：不管角色，按钮都亮 ✅
- 现阶段开发者自用，升级（growing→golden）和标注（accept/reject）按钮对所有登录用户可见可操作
- 不实现 maintainer/annotator 角色区分，后端的 maintainer_token 约束在前端层不做拦截（后端是否仍校验，取决于现有 API 实现是否强制）

---

### D7. 待标注 accept 的交互（对齐后端 DecideRequest）✅
对齐后端 `POST /api/promote/tasks/{id}/decide` 的 `DecideRequest` 结构：
- **decision**：`accept` | `reject` 二选一（reject 最简单，标记不入库）
- **accept 必须二选一**（后端强制校验，缺则 400）：
  - **归入已有 case**：填 `target_case_id`（从 growing 层现有 case 下拉选）
  - **新建 case**：填 `new_case_title`（标题）+ `demand_md`（标注者规范化的需求文本）
- **reference_output**：可选，留空则后端自动从 trace 的 `user_edit` 事件提取编辑终稿
- annotator 字段：后端默认 "anonymous"，前端可传当前登录用户名

---

### D8. 待标注 Tab 的数据来源：自动（无需手动触发）✅
- 后端 `promote/scheduler.py` 后台调度器（`start_judge_scheduler`，启动即在 lifespan 挂载，5 分钟扫一次）自动运转：
  1. **发现**：`runs` 表里 `run_purpose='user_generation'` 且 `status='completed'` 且无 promote_task 的 trace → 自动 `create_task`（pending）
  2. **judge**：对 pending 任务自动跑 filter + scoring → 推进到 `needs_confirm`（等人工确认）/ `rejected`（auto_reject）
- 结论：只要执行端有生产 trace 完成，**「待标注」Tab 就会有真实数据流入**，页面纯消费即可，不需要在数据集页加「手动建 task」入口。

### D9. 升级 maintainer_token：开发模式不校验 ✅
- 后端 `PromoteRequest`：`maintainer_token` 来自 `settings.maintainer_token`，**配置为空则不校验**（开发模式）。
- 结论：前端升级按钮不传 token 也能成功（开发环境）；生产环境若配了 token，前端需从某处读取后传——但这属于 D6「不管权限」的延伸，现阶段不阻塞，后端空配置即可。

---

### D10. 待标注 task 的展示形态：行内操作 + trace 跳转 ✅
- 待标注表格每行精简显示 judge 分数（带颜色徽章，如高分绿/低分红）+ verdict + trace_id（可点击跳转到 `/traces/:traceId` 详情页看全貌）
- accept/reject 操作**直接在行内**完成，不进独立详情页
- accept 时弹出表单：归入已有 case（下拉选 growing case）/ 新建 case（填 title + demand_md）+ reference_output（可选）
- judge 分数想看明细：点 trace_id 跳转 trace 详情页

### D11. Golden case 详情：本期不做 benchmark 历史 ✅
- Golden Tab 的 case 详情本期只展示 demand.md 全文 + reference.md（如有）+ 元数据
- benchmark 跨版本矩阵（`/api/benchmark/leaderboard`）**本期不接入**，留作后续迭代
- 理由：当前数据集本身可能为空，benchmark 跑分多半也还没数据，先把数据闭环主体做出来

### D12. 导航位置：Agent要素 与 单次测试 之间 ✅
- 侧边栏导航顺序变为：监测 / 评估 / 进化 / Agent要素 / **数据集** / 单次测试 / 配置
- 理由：数据集是测试的输入素材，紧跟 Agent要素（测试另一输入）认知流最顺

### D13. API 封装范围：仅封装本期用到的 6 个端点 ✅
桌面端 `lib/api.ts` 新增封装（通过现有 `apiFetch`/`apiJson` 走 Tauri http 中继）：
- `GET /api/dataset/cases?layer=` — Golden/Growing 列表
- `GET /api/dataset/golden-revision` — golden 指纹（Golden Tab 头部展示）
- `POST /api/dataset/cases/{id}/promote` — 升级按钮
- `GET /api/promote/tasks` — 待标注列表
- `GET /api/promote/tasks/{id}` — task 详情（拿 judge 分数）
- `POST /api/promote/tasks/{id}/decide` — accept/reject

benchmark 端点（`/api/benchmark/*`）**本期不封装**，留到 D11 后续迭代接入时再写。

### D14. 错误处理：最小处理 ✅
- 写操作（升级 / accept / reject）失败时，catch 错误，用项目现有的 `sonner` toast 弹错误提示
- 不做自动重试
- GET 请求失败沿用现有页面惯例（已有页面怎么处理列表加载失败就怎么处理）
