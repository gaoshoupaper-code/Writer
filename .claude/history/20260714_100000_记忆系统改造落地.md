# 记忆系统改造落地（需求文档）

## 核心诉求

spike（P0 验证）**4/4 全过**，进入设计方案的 P1-P3 落地阶段——把 Graphiti + NWM 叙事学 schema 的记忆系统真正接入 Writer 的 executor/evolution 代码，替换现有"全量文件注入"的记忆机制，实现"按需检索 + 状态演变建模 + 可随使用迭代进化"。不做 P4（一致性检测规则层）。

## 已确认决策

| 决策项 | 结论 | 依据 |
|--------|------|------|
| spike 结果 | 4/4 全过 | 中文抽取/历法/别名/成本四项都达 pass 标准 |
| 技术路线 | Graphiti 全量接入（不走退路 C） | spike 决策门：4/4 Pass → P1 Graphiti 全量 |

| 分支策略 | 从 main 新建 feat/memory-system 分支 | spike 分支保留不动 |

## 设计方案伪代码与真实代码的关键差距（落地时必须处理）

> 这些是探查代码发现的事实，设计方案未覆盖，需要在改造时对着真实代码调整。

1. **`state.current_chapter` 不存在**：章节号是运行时从 task description 正则提取的（`executor/app/domains/writing/events.py:_extract_chapter_index`），不持久化进 State。memory_recall_middleware 构造查询时拿不到现成章节号。
2. **没有"章节发布钩子"**：章节落盘是 writing 子代理用 write_file 工具完成的。middleware 的 wrap_tool_call 抓不到 subagent task 调度（events.py:16-19 注释明确）。唯一的"章节完成"感知在 SSE 层 `WritingEventSink._on_writing_chapter_done`。
3. **harness 已"去 DB 重构"**：`manifest.json`/`snapshot_repo`/`config_diff` 已废弃，现在是 `registry.json` + git 独立仓库。设计方案伪代码引用的旧结构需对齐。

## P1 骨架决策（本轮挖掘结论）

### 决策 1：Graphiti 接入——可进化 vs 固定基础设施分离

| 部分 | 归属 | 内容 |
|------|------|------|
| **固定基础设施** | 执行端管理，走 RuntimeContext 注入 | FalkorDB 连接、Graphiti 客户端实例、add_episode/search API 调用、入图管道（SSE sink 触发 + 异步队列 + group_id 隔离） |
| **可进化部分** | harness 包内，evolution 能改 | ①抽取 prompt + schema 定义（entity_types/edge_types）②memory_recall_middleware 检索策略（查询构造/四阶段参数/证据包组装）③StoryCalendar 映射规则 |

落地形态：`RuntimeContext` 增加 `graphiti_client` 字段（同 trace_recorder 模式）；可进化部分落 `harnesses/repo/middleware/memory_recall_middleware.py` + `prompts/extraction_*.md` + `tools/narrative_schema.py`。

### 决策 2：章节入图钩子——SSE sink + 异步队列

落点 `WritingEventSink._on_writing_chapter_done`（唯一可靠感知章节完成的点），触发异步入图队列，不阻塞 SSE 流。

### 决策 3：storyline 进图——分两层，Thread/StoryNode 提到 P1

"storyline 进图"分两层：
- **A. storybuilding 蓝图层**：storybuilding 产物（storyline/character/worldview）一次性入图，全局参考，不受章节作用域限制。Thread + StoryNode 作为核心实体。
- **B. 章节发布层（Causal）**：每写完一章正文入图，受章节作用域限制（查询第 N+1 章只能用 ≤N 的更新）。

**P1 schema 扩展**（原设计方案 P1 只上 Character/Relationship/Location，现扩展）：
- Character / Location / WorldFact（来自 storybuilding 的 character/worldview）
- Thread / StoryNode（来自 storybuilding 的 storyline/S0X + timeline）
- Relationship 边（参与角色/所在地点/事件归属故事线/事件组包含）
- 暂不上 Promise（伏笔状态机，留 P2）

依据：Writer 现有 storyline 结构（S0X-*.md 的事件 E0XX 带 类型/参与角色/地点/时间）已是高度结构化的叙事分解，天然可入图，不入图太浪费。

### 决策 4：memory_recall 与 ContextAssembler 分工

memory_recall 对 writing 子代理做**主体替换**：
- character/storyline/worldview → 走图检索（memory_recall 召回）
- detail_outline（当前章写作意图，"要写什么"而非"世界事实"）→ 仍由 ContextAssembler 注入，或并入查询条件

### 决策 5：storybuilding 入图用结构化抽取（非 Graphiti 默认 episode 抽取）

storyline 的 E0XX 事件 + character + worldview 本就是高度结构化的 markdown，用专门的解析器按 schema 直接建节点/边，不依赖 LLM 猜。抽取质量可控，比 Graphiti 默认 episode 抽取靠谱。

### 决策 6：StoryCalendar 双模式

作品级配置"纪年模式"：公元（科幻/都市/言情，直接转 datetime）或虚构（玄幻/武侠，需 epoch + 历法规则）。spike2 已验证虚构历法可行。

### 决策 7：detail_outline 产物是 memory_recall 的查询条件来源（关键发现）

detail_outline 产物 `detail/chapter-XX.md` 是高度结构化的章节指令（6 固定小节：本章事件/本章目标/主爽点/出场人物/线索推进/章末钩子），不是散文。

**完整数据流（已确认）**：
```
storybuilding 产物（storyline/character/worldview）
    ↓ [决策5：结构化抽取入图]
Graphiti 图谱（Thread/StoryNode/Character/Location/WorldFact + 关系边）
    ↑                                    ↑
    │ memory_recall 用 chapter-XX.md     │ Causal：章节正文入图
    │ 的"本章事件+出场人物"构造查询      │
writing 子代理 ← detail/chapter-XX.md（写作意图，文件注入，writing 自行 read）
```

**writing 子代理的信息来源（双通道，已确认）**：
1. task description（meta→writing）：章节编号/目标/爽点/出场人物/线索推进
2. 文件 read（writing 自行）：`detail/chapter-XX.md`（细化指令）+ `chapter/` 前 5 章（前文上下文）
   - 注意：`detail/*.md` 刻意不进 ContextAssembler 注入（超落盘阈值），writing 按需 read

memory_recall middleware 在 writing 的 before_model hook 注入图检索结果，与 writing 自行 read 的 detail/chapter-XX.md 互补。

### 决策 8：多作品隔离用 workspace 标识（group_id）

Graphiti 的 group_id 参数用 workspace 标识（owner_id + thread_id 组合）。每个作品一个独立子图，与现有 workspace 隔离机制一致。

### 决策 9：P1 验证用"科幻小说" workspace

已有完整 storybuilding 产物（storyline/character/worldview），先验证 storybuilding 入图 + 检索，再跑一个完整写作流程（detail_outline→writing）验证端到端。

### 决策 10：记忆系统失败即报错中断（用户明确选择）

FalkorDB 挂了 / 抽取失败 / 检索超时 → 报错中断写作流程，**不降级到 ContextAssembler 全量注入**。

> ⚠️ 产品影响提示（已向用户说明，用户坚持此选择）：
> 这意味着记忆系统从"增强层"变成了"依赖层"——FalkorDB 故障会阻塞创作。
> 设计方案 §9.2 风险清单里 FalkorDB 运维是"低概率中影响"，此选择将其升级为"中概率高影响"。
> 落地时需配套：FalkorDB 健康检查 + 自动重启 + 监控告警，把可用性拉高。

### 决策 11：md→graph 单向同步

md 是人读真相源，graph 从 md 派生。作者改 md 后，下次入图/检索时从 md 重建对应部分。与设计方案 §3.1"叠加而非替换"一致。需配套 md 变更检测机制（留设计阶段）。
