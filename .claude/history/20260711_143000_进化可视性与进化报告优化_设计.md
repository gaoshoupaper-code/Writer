# 进化可视性与进化报告优化 · 设计方案

## 架构方向（待确认）

三端协同改动，数据链路打通：

```
评估Agent ──产出findings(带id)──→ DB
                                      │
进化启动 ──加载eval_snapshot(含findings)──→ plan子代理context
                                      │
plan子代理 ──填evidence_ref(引finding.id)──→ write_design_doc(硬校验)
                                      │
execute子代理 ──产出change_log──→ DB
                                      │
桌面端审查视图 ←─ session API返回文档内容 ─→ 后端读盘+组装
```

**三端改动范围**：
- **评估端**（最小）：`write_eval_report` 工具 + prompt → findings 加 id（兜底补）
- **进化端**（中等）：`write_design_doc` 加 evidence_ref 字段 + 硬校验；session API 返回文档内容
- **桌面端**（最大）：新建审查视图组件 + API 封装 + evolve.tsx 加入口

## 已确认决策

### D1 — 数据管子：内联进 get_session
`GET /evolve/sessions/{id}` 详情接口里，当 `design_doc_path`/`change_log_path` 非空时，读盘对应 .md 文件，解析 front matter，把结构化内容塞进返回体：
- `design_doc: { meta: {changes:[...]}, body: string } | null`
- `change_log: { meta: {applied:[...], validation:{...}}, body: string } | null`
- 列表接口 `list_sessions` 不变（保持轻量，不读盘）。
- 同时内联关联的评估 findings（通过 `eval_ref` 查 evaluation_sessions，把 findings 带上），供审查视图渲染证据卡片。

### D2 — 审查视图：全屏路由
路由 `/evolve/:sessionId/review`，独占屏幕。
- 列表页 evolve.tsx 的 session，pending_review 状态时显示"审查"按钮 → 导航到审查路由。
- 审查页布局：顶部 session 元信息 + 分数对比；主体改动清单（逐条卡片）；底部 sticky 发布/丢弃。
- 非 pending_review 状态（running/failed/published/discarded）也可进入查看，但无发布/丢弃按钮（已发布的看历史报告）。

### D3 — 方案落地对照：显式关联字段
execute 子代理产 change_log 时，每条 `applied` 记录新增 `design_ref` 字段，引用 design_doc 中对应 change 的序号（如 `1` 表示 design_doc 的第 1 条 change）。
- 前端对照：design_doc 的 changes 按 index 展开，每条找 change_log.applied 里 `design_ref === index` 的记录，标注落地状态。
- 无匹配 applied 的 change → 标"未落地"高亮。
- 需改 execute 子代理的 `write_change_log` 工具 docstring + prompt。

### D4 — evidence_ref：多值数组
design_doc 每个 change 的 `evidence_ref: string[]`，引用一个或多个 finding.id。
- 含义：一条改动可能同时解决多个评估发现的问题，多值诚实反映完整关联。
- `write_design_doc` 校验：`evidence_ref` 必须非空数组，且每个值必须存在于当前 session eval_snapshot 的 finding_ids 集合中。

### D5 — finding id：工具强制重编号
`write_eval_report` 工具解析 findings 后，**不管 Agent 产什么 id，统一重新编号**为 `f01`/`f02`/...（两位数字符串）。
- 彻底规范，杜绝 Agent 产出格式混乱（f1/F01/finding_1 混杂）。
- 下游（进化 Agent 填 evidence_ref、前端展示）面对的永远是规范 id。
- prompt 仍要求 Agent 产 id（保持 Agent 理解"每条要有标识"），但工具覆盖为准。

### D6 — 评估数据内联范围：findings + scores
session API 内联关联评估的 `findings` + `scores`，不带 `report_md`。
- findings：供审查视图的证据卡片（含 id/dimension/severity/finding/evidence）。
- scores：供基线分 vs 候选分对比。
- report_md 是评估全文，审查视图不需要（审查只看 finding 级证据）。

## 数据模型变更汇总

### finding（评估端，加 id）
```python
# write_eval_report 工具强制重编号后，每条 finding：
{
  "id": "f01",           # ← 新增，工具强制生成
  "dimension": "...",
  "severity": "high|medium|low",
  "evidence_type": "实证|推断",
  "finding": "...",
  "evidence": "...",
}
```

### change（进化端 design_doc，加 evidence_ref）
```python
# design_doc.md 的 meta.changes 每条：
{
  "target": "...",
  "change_desc": "...",
  "reason": "...",
  "expected_up": "...",
  "expected_down": "...",
  "evidence_ref": ["f01", "f03"],  # ← 新增，必须非空，引用 finding.id
}
```

### applied（进化端 change_log，加 design_ref）
```python
# change_log.md 的 meta.applied 每条：
{
  "target": "...",
  "action": "edit_file|write_file|apply_edits",
  "result": "ok|failed",
  "detail": "...",
  "design_ref": 1,  # ← 新增，对应 design_doc.changes 的序号（1-based）
}
```

## 接口契约

### GET /api/evolve/sessions/{session_id}（改造：内联文档内容）
**改动**：`get_session` 返回体新增三个内联字段（均为 null 时表示无文档/读盘失败）。

```typescript
// 返回体新增字段（原有字段省略）
{
  // ... 原有 session 字段不变 ...
  design_doc?: {
    meta: {
      designed_at: string;
      changes_count: number;
      changes: Array<{
        target: string;
        change_desc: string;
        reason: string;
        expected_up: string;
        expected_down: string;
        evidence_ref: string[];  // 引用 finding.id
      }>;
    };
    body: string;  // markdown 正文
  } | null;
  change_log?: {
    meta: {
      executed_at: string;
      applied_count: number;
      applied: Array<{
        target: string;
        action: string;
        result: "ok" | "failed";
        detail: string;
        design_ref: number;  // 对应 design_doc.changes 序号
      }>;
      validation: { passed: boolean; config_valid: boolean; import_ok: boolean; errors: string[] };
    };
    body: string;
  } | null;
  eval_snapshot?: {  // 关联评估（通过 eval_ref 查 evaluation_sessions）
    findings: Array<{
      id: string;  // f01/f02...
      dimension: string;
      severity: string;
      evidence_type: string;
      finding: string;
      evidence: string;
    }> | null;
    scores: Record<string, unknown> | null;
  } | null;
}
```

**实现要点**：
- `get_session` 查到 session 后，若 `design_doc_path` 非空 → 调 `docs.read_design_doc()`（已有）解析；`change_log_path` 非空 → 调 `docs._load_doc()` 解析。
- 若 `eval_ref` 非空 → 查 `eval_repo.get_session(eval_ref)` 取 findings + scores。
- 读盘失败时对应字段设 null，不抛异常（R8：残缺不崩）。

## 入口策略（D2 延伸）

evolve.tsx 列表/详情区的 session，按状态显示不同按钮：

| status | 按钮 | 行为 |
|---|---|---|
| `running` | "查看进度" | 留在原 SSE 流水（不变） |
| `pending_review` | "🔍 审查" | → `/evolve/:id/review`（含发布/丢弃） |
| `published` | "查看报告" | → `/evolve/:id/review`（只读，无发布/丢弃） |
| `discarded` | "查看报告" | → `/evolve/:id/review`（只读） |
| `failed` | "查看失败" | → `/evolve/:id/review`（走 R8 残缺渲染） |
