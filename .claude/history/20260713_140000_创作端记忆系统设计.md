# 创作端 Agent 记忆系统设计（v2 —— 复盘修正版）

> 需求来源：`agent_memory_system/report.md`（19 对象调研）
> v2 变更：经深度复盘修正 3 个致命想当然 + 2 个中等问题（见附录 A）

---

## 一、已确认决策总表

| 决策 | 结论 | 理由 |
|------|------|------|
| **技术路径** | 路径 B：时序知识图谱 | 双时间戳直击角色漂移/时间线/伏笔 |
| **记忆引擎** | Graphiti（Apache-2.0）+ FalkorDB 后端 | 成熟双时间戳模型；FalkorDB 轻量 SSPL |
| **记忆边界** | per-workspace（group_id=workspace_id） | 作品间不共享 |
| **真相源** | .md 文件是创作产物真相源，图谱是派生索引 | 用户手改 .md 后重抽同步 |
| **写入责任方** | memory_keeper 子代理（LLM 编排 + tool 操作图谱） | 与现有 meta 委托模式同构 |
| **抽取 LLM** | Graphiti 用 ctx.model 初始化（走用户 key）+ 和创作一起收费不另扣积分 | token 用户直付，积分不重复计 |
| **一致性检测** | 进 memory_keeper（check_consistency tool） | 抽取后顺手比对图谱 |
| **代码位置** | P3 分层：创作策略进包可进化，基础设施进平台层稳定 | |
| **Schema** | 深度定制 Pydantic 实体/边类型，章节级抽取 | 检索精准 |
| **失败策略** | 软失败继续（记忆是增强层） | 挂了退化到全量注入 |
| **触发机制** | prompt+skill 约束 LLM（Phase 4 验证漏调严重再加中间件） | 最小侵入 |
| **初始化** | storybuilding 后专门初始化 + 产出 ch1 快照 | 建图谱地基 |
| **读取路径** | **快照文件模式**（见 §五，v2 关键修正） | ContextAssembler 几乎不改 |

## 四、memory_keeper 子代理形态（v2 关键修正）

### 核心认知修正

**DeepAgent 子代理是"LLM + tool + middleware"的隔离 graph，不是任意 Python 执行环境。** memory_keeper 不能"内部直接调 graphiti.add_episode()"——它只能调被装配进去的 tool。

### memory_keeper 结构

```
memory_keeper 子代理（LLM 编排：读章节 → 决策抽取 → 调 tool → 产出快照）
  ├─ tool: extract_chapter(chapter_num)  
  │    → 读 chapter/N.md → Graphiti.add_episode → 返回抽取的实体/事件
  ├─ tool: check_consistency(chapter_num)
  │    → Graphiti.search 取 canon → ConStory 比对 → 返回矛盾列表
  ├─ tool: query_memory(query)  
  │    → Graphiti.search → 返回相关记忆（供快照组织用）
  └─ tool: write_snapshot(chapter_num, content)
       → 写 memory/snapshot-{N+1}.md（下一章所需记忆快照）
```

**tool 持有 Graphiti client**：三 tool 在装配时通过 middleware_factory 闭包捕获 `ctx.graphiti_client` + `ctx.workspace_id`（client 不进 RuntimeContext 的可选字段则 tool 内部缓存）。这是子代理访问图谱的**唯一通道**。

### memory_keeper 规格表

| 维度 | 决策 | v2 修正说明 |
|------|------|------------|
| 职责 | 抽取 + 检测 + 产快照 | 三合一 |
| LLM | ctx.model（编排决策走 graph，被 CreditsMiddleware 计费累加到 hold） | Graphiti 抽取 LLM 走 ctx.model 但绕过 middleware（用户 key 直付 token，不另扣积分） |
| 触发 | prompt+skill 约束 meta 每章后委托 | **非自动**，靠 LLM 自觉（v2 明确） |
| 权限 | 读 /** + 写 /memory/** | 不碰 /chapter/**（writing 专属） |
| 角色/章号来源 | 自己 read detail/chapter-XX.md + chapter/ 目录 | **不从 task_text 解析**（v2 修正，避免脆弱正则） |

### RuntimeContext 扩展（必须）

`contracts/runtime_context.py` 加两字段：
```python
graphiti_client: object | None = None   # Graphiti 实例（executor 侧初始化传入）
workspace_id: str | None = None          # 当前 workspace（group_id 用）
```
executor 侧 `_assemble_via_package`（`agent.py:92`）构建 ctx 时：按 workspace 初始化 Graphiti client（用 ctx.model），设 group_id=workspace_id。

## 五、读取路径：快照文件模式（v2 关键修正）

### 原方案（废弃）：ContextAssembler 直连图谱
- ❌ ContextAssembler 要持有 Graphiti client（平台层中间件直连图谱，稳定性要求高）
- ❌ 从 task_text 解析角色名（脆弱正则）
- ❌ ContextAssembler 一次性注入，与"每章不同记忆"时序冲突

### v2 方案：memory_keeper 产出快照，ContextAssembler 读文件

```
写入侧（memory_keeper，每章后）：
  抽取 chN → query_memory(本章角色当前状态 + 活跃伏笔 + 时间线)
           → 组织成 memory/snapshot-{N+1}.md（markdown，供下一章注入）

读取侧（ContextAssembler，几乎不改）：
  writing 写 chN → ContextAssembler 读 memory/snapshot-{N}.md（加进 file_paths）
                 → 注入 prompt（和现有 outline.md/character/*.md 同列）
```

**为什么这个方案更优**：
1. **ContextAssembler 几乎不改**——它本来就读 .md，快照只是 `file_paths` 加一项（动态：读 `memory/snapshot-{当前章号}.md`，但章号怎么定见下）
2. **图谱复杂性全隔离在 memory_keeper**——平台层 ContextAssembler 不碰图谱
3. **天然软降级**——memory_keeper 失败没产快照，ContextAssembler 读不到就跳过，退化为现有全量注入（零代码改动降级）
4. **时序自洽**——storybuilding 后 keeper 产 ch1 快照；写 chN 前已有 chN 快照（chN-1 抽取时产出）

### 快照内容结构（memory/snapshot-{N}.md）

由 memory_keeper 的 LLM 组织（基于图谱查询），包含：
```markdown
# 第 N 章记忆快照
## 出场角色当前状态（截至第 N-1 章）
- 张三：位于边疆，持玄铁剑，与李四关系=敌对（ch15 背叛后），心理=复仇
- 李四：位于京城，身份暴露，已知张三下落
## 活跃伏笔（未回收）
- [planted ch3] 神秘玉佩的来历 — 待回收
- [planted ch12] 李四的卧底身份 — 已回收 ch15
## 时间线锚点
- 当前故事时间：建元二十年冬
- 上章末：张三离京北上
## 本章相关 canon（防漂移）
- 世界规则：玄铁剑只认主血脉
```

### "当前章号"如何确定（ContextAssembler 读取侧）

ContextAssembler 的快照路径用 Callable：
```python
file_paths=[..., lambda task_text: _snapshot_path(workspace)]  # 读 chapter/ 目录计数
```
`_snapshot_path`：读 `chapter/` 目录已有章数 +1 = 将写章号 → 返回 `memory/snapshot-{N}.md`（不存在则返回空，跳过）。**不依赖 task_text 解析**，靠文件系统状态——稳定。

## 六、数据与状态（图谱 Schema）

### Schema 策略
深度定制 Pydantic 实体/边类型；章节级抽取（一 chapter.md = 一 Episode）。

### 实体类型

| 类型 | 对应 .md | 关键属性 | 时序性 |
|------|---------|---------|--------|
| `Character` | character/*.md | name, aliases[], role, appearance, personality, current_state | 静态+动态 |
| `Location` | worldview.md | name, description, parent_location | 静态 |
| `Item` | storyline/detail | name, description | 持有者会变 |
| `Faction` | worldview.md | name, ideology | 成员会变 |
| `PlotThread` | storyline/*.md | name, status(open/dormant/closed) | 强时序 |
| `Foreshadow` | 抽取发现 | planted_chapter, status(planted/hinted/resolved), payoff_chapter | 强时序三态 |

### 边类型（双时间戳 valid_at/invalid_at，旧事实只失效不删除）

| 边类型 | 含义 |
|--------|------|
| `RELATES_TO` | 角色关系（relation_kind: 信任/敌对/师徒/恋人） |
| `LOCATED_AT` | 角色在某地 |
| `HOLDS` | 持有物品 |
| `PARTICIPATES` | 参与事件 |
| `PLANTED_AT`/`RESOLVED_AT` | 伏笔埋设/回收 |
| `MEMBER_OF` | 隶属阵营 |

### Episode + workspace 隔离
每章 = Episode，实体提及经 MENTS 二部边锚定（E²RAG，解决角色状态混并）。`group_id=workspace_id` per-workspace 物理隔离。

## 七、接口契约 + 降级

### 三个 tool 接口（memory_keeper 调用）

```python
# extract_chapter：抽取并写图谱
async def extract_chapter(chapter_num: int) -> str:
    text = read(f"chapter/chapter-{chapter_num}.md")
    await graphiti.add_episode(name=f"chapter-{chapter_num}",
        episode_body=text, reference=Title(f"/chapter/{chapter_num}.md"),
        group_id=workspace_id, source=EpisodeType.text)
    return "已抽取第{chapter_num}章，实体/事件：..."

# check_consistency：一致性检测
async def check_consistency(chapter_num: int) -> list[Conflict]:
    canon = await graphiti.search(query=f"第{chapter_num}章 canon",
        group_ids=[workspace_id])
    return consistency_checker.check(chapter_text, canon, constory.CATEGORIES)

# write_snapshot：产出下一章快照（LLM 组织后写文件）
async def write_snapshot(chapter_num: int, content: str) -> str:
    write(f"memory/snapshot-{chapter_num}.md", content)
    return "快照已写"
```

### 降级策略（记忆是增强层）

| 失败点 | 策略 |
|--------|------|
| FalkorDB 连接失败 | keeper 软失败，不产快照；ContextAssembler 读不到快照跳过→全量注入 |
| Graphiti 抽取失败 | keeper 标记未抽取，继续流水线，下章重试 |
| 检测报矛盾 | 记 warning 到 review/*.md，不阻塞 |

### 初始化流程（storybuilding 后）

```
1. 遍历 character/*.md → Character 实体（valid_at=ch0）
2. 遍历 storyline/*.md → PlotThread 实体
3. worldview.md → Location/Faction
4. query_memory(初始角色状态) → 产出 memory/snapshot-1.md（第一章快照）
```

## 八、计费设计（v2 修正）

| 调用 | 走 DeepAgent graph？ | CreditsMiddleware 捕获？ | 计费方式 |
|------|---------------------|------------------------|---------|
| memory_keeper 编排 LLM（子代理决策） | 是 | 是 | 累加到创作 hold（和 writing 同 hold） |
| Graphiti 抽取 LLM（add_episode 内部） | 否（Graphiti 私有 client） | 否 | 走 ctx.model 用户 key，token 用户直付，**不另扣积分** |
| 检测 LLM（consistency_checker） | 取决于实现 | 若用 ctx.model 直调则否 | 同上，不另扣 |

**用户决策**："和创作一起收费" = memory_keeper 编排算进创作 hold；Graphiti 抽取 token 用户 key 直付，平台不重复扣积分。

**必须改的代码点**：
- `_CREATION_SUBAGENTS`（`middleware.py:33`）加 `"memory_keeper"` —— 否则 storybuilding 后初始化时无 hold，编排 LLM 漏计

## 九、触发设计（v2 修正：prompt 约束）

### meta_system.md / skill 改动

`auto-pipeline/SKILL.md` 流程加一步：
```
正文循环：
  writing（写 chN）→ memory_keeper（抽取 chN + 产 chN+1 快照 + 检测）→ 下一章 writing
```
`meta_system.md` 加：storybuilding 完成后、detail_outline 前委托 memory_keeper 初始化。

### 漏调风险与兜底
- 风险：LLM 跳过 memory_keeper 直接写下章 → 该章无快照，ContextAssembler 跳过注入（退化为全量 .md），不崩但记忆断档
- 监控：trace 检查每章后是否有 memory_keeper-subagent 事件（Phase 4 验证漏调率）
- 若 Phase 4 发现漏调严重 → 加 meta 中间件 `wrap_tool_call` 拦截 task(writing) 返回强制注入 keeper 提示（届时再上）

## 十、WBS 任务拆解

### Phase -1：Spike 验证（4 个致命点，先于一切）

> 目的：在投入完整 WBS 前，用最小代价验证 4 个致命假设。任一 fail 则回退到路径 C 或 A。

#### Spike 1：中文抽取验证
- **假设**：Graphiti 能从中文小说正文抽取出纯中文实体名/关系
- **做法**：写一段中文小说（~500字，含角色+地点+物品+关系），调 `graphiti.add_episode`，检查产出实体 name/summary 是否纯中文
- **Pass 标准**：产出实体名 ≥90% 纯中文，无中英混杂
- **Fail 退路**：若覆写 prompt 后仍混杂 → 评估是否回退路径 C（sqlite-vec）
- **关键变量**：是否需覆写 graphiti_core/prompts/，覆写后效果

#### Spike 2：虚构历法验证
- **假设**：自定义 StoryCalendar 能把"建元二十年冬"正确转成 datetime，使 Graphiti valid_at 推算合理
- **做法**：实现最小 StoryCalendar（建元元年=锚点，章→天偏移），传 reference_time，加一段"三年前结拜"正文，检查 valid_at
- **Pass 标准**：valid_at 落在合理区间（结拜早于当前章 3 年）
- **Fail 退路**：valid_at 推算不可靠 → 退化用章节号当时间锚点（ch0..chN 而非真实日期）

#### Spike 3：别名消歧验证
- **假设**：连续 add_episode 能把"张三/张大侠/张公子"合并成 1 个节点
- **做法**：准备 3 段文本分别含三种称呼，连续 3 次 add_episode，查图谱节点数
- **Pass 标准**：合并成 1 节点（或加"规范名预处理"后合并成 1）
- **Fail 退路**：产生 3 节点 → 必须上规范名表预处理层（storybuilding 产别名映射，抽取前替换）

#### Spike 4：成本 dry-run
- **假设**：单章抽取的 LLM 调用次数 + token 量在可接受范围
- **做法**：用真实 1 章正文（~1000字）跑完整 add_episode，埋点记录 LLM 调用次数 + token 总量
- **Pass 标准**：单章 ≤15 次 LLM 调用，token ≤20k（可接受阈值，待定）
- **Fail 退路**：成本过高 → 评估分层模型(small_model 跑 dedup)/combined extraction/或回退路径 C

#### Spike 产出
每个 spike 输出一份 verdict.md（pass/fail + 数据 + 证据），汇总决定是否进 Phase 0。

## 十二、轮次 7 查证：Graphiti schema 真相（新增）

经深度查证 Graphiti 官方文档/GitHub issue，3 个关键假设的验证结果：

### ✅ 成立的假设
- **自定义 Pydantic 类型能被 LLM 真分类**（非贴标签）：Graphiti 把 Pydantic 序列化为 JSON Schema 注入抽取 prompt + 用 Structured Output 强制 LLM 按 schema 返回。**但必须每次 add_episode 显式传 entity_types**（Issue #1308：漏传全是默认 Entity）
- **LLM 可配置**（接 ctx.model）：子类化 LLMClient 接 OpenAI-compatible，但**必须支持 Structured Output**
- **跨章实体合并**：机制在（MinHash+LSH+LLM 消歧），但小说别名高危

### ⚠️ 3 个必须改造的工程点

**改造 1：中文 prompt 全链路覆写**
Graphiti 内置 prompt 默认英文，产出中英混杂（Issue #312），对创作致命。
→ 覆写 `graphiti_core/prompts/` 下 extract_nodes/edge/dedupe/resolve 等，统一加"输出简体中文"

**改造 2：虚构纪元 → datetime 映射层**
Graphiti valid_at 是真实 datetime，不懂"建元二十年冬"。
→ 自建 StoryCalendar：storybuilding 定义虚构历法 → 每章转真实 datetime 作 reference_time → 相对时间预抽取成绝对故事日期

**改造 3：规范名表 + 初始化用循环非 bulk**
小说别名（张三/张大侠/张公子）消歧高危（Issue #963）；bulk 跳过 edge invalidation。
→ storybuilding 产规范名表 → 抽取前别名替换主名 → 初始化循环 add_episode（非 bulk）

### 📊 成本真相
单次 add_episode = **5-15+ 次 LLM 调用**（抽取+去重+边 resolve+时间戳+embedding）。小说单章实体密度高，可能 10+ 次。memory_keeper 每章成本远超"多一轮"。

### 💣 版本陷阱
- Issue #1489：增量回填 reference_time 被硬编码 now()，时间戳错乱 → 锁已修版本
- Issue #1616：OpenAI provider 忽略 api_url，自定义 endpoint 可能失效 → 接 ctx.model 前验证
