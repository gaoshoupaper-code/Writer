# 创作端对话执行 UX 重设计方案

## 设计目标

基于已冻结需求（详见 20260710_130000_创作端对话执行UX重设计.md），把创作端 Agent 执行过程从"冷的状态报表"重做为"有温度的 AI 写作伙伴'小衍'在工作的过程"。

核心理念：信息丰富化 × 小衍人格 × 双驱动重构，前后端两期交付。

## 勘察关键发现（影响设计路径）

### 发现 1：reasoning token 是"最后一公里"（利好）
`DeepSeekThinkingChatModel`（`executor/app/domains/writing/deepseek_thinking.py`）已完整实现 reasoning 的提取、流式分块、回填。流式 chunk 的 `additional_kwargs["reasoning_content"]` 已被测试覆盖（`test_writer_models.py:156-172`）。
**当前被丢弃**：`events.py:222-231` 的 `on_chat_model_stream` 只读 `chunk.content`，忽略 `additional_kwargs`。
→ 后端改造只需加几行转发逻辑。

### 发现 2：预估进度的数据已有"省方案"
- **已有**：`tool_call` 帧已带 `total_chapters`（`events.py:261-275`），前端零改动即可展示"第 X/Y 章"。
- **没有**：真正的预估时间需新建历史 trace 聚合层（扫 jsonl 算 P50/P90），工作量大。
→ 可降级：P1 先做章节进度（零后端改动），真正的预估时间推迟或用简单算法。

### 发现 3：事件源是 LangGraph 的 astream_events，不是 DeepAgent 回调
reasoning token 只能通过 `astream_events` 的 `on_chat_model_stream` 拿到 chunk 上的 `additional_kwargs`，DeepAgent 的 `AgentMiddleware` 只有调用级钩子，没有 token 级钩子。
→ 改造点明确在 `WritingEventSink.on_event`，不在 DeepAgent 框架内部。

## 主路径方向（第 1 轮确认）

**分层重构 + 渐进替换**：
1. 先抽离执行编排层（home.tsx 里的 performSubmit/SSE 循环/状态机），为新 UI 提供干净的数据接口
2. 新建"小衍"执行体验组件层（ExecutionView + 子组件），替换现有的 StageFlowView 在对话流内的角色
3. 后端最小改造（reasoning 转发 + 预估数据）

不推荐"一次性重写全部"——home.tsx 承载的功能太多，一口气全重写回归风险极高。

## 架构基石（第 1 轮确认）

### ① 状态管理 = Zustand 多 Store
- 按领域拆 store：`useExecutionStore`（SSE/状态机/小衍数据）、`useWorkspaceStore`（工作区/会话）、`useTraceStore`、`useContentStore`。
- 组件直接订阅所需 store，home.tsx 瘦成纯编排壳（目标 <200 行）。
- 选型理由：轻量（~1KB）、无 Provider 嵌套、TS 友好、已有项目无状态管理库引入。

### ② 小衍组件层 = 单一 ExecutionView 容器
- 一个 `ExecutionView` 组件接管执行过程的全部渲染（黑屏期/思考流/进度/交付），内部按 `executionPhase` 切换子视图。
- ChatPanel 只调 `<ExecutionView phase={...} reasoning={...} progress={...} />`。
- StageFlowView 的角色被 ExecutionView 取代（但底层 stage 数据派生逻辑保留复用）。
- 内聚度高，对话流干净。

### ③ 预估时间 = P1 章节进度，P2 推迟真预估
- **P1**：只做"第 X/Y 章·约 N 字"进度展示（后端 `total_chapters` 数据已有，零改动）。
- **P2 或后续**：真预估时间推迟，届时用简单算法（前端单章耗时历史线性外推）或后端聚合层。
- 务实优先：不为准头牺牲 P1 周期。

## ExecutionView 状态机（第 2 轮确认）

### 体验阶段（executionPhase）—— 细分 5 态

```
idle（待机）
  ↓ [用户发送]
booting（黑屏期·优雅骨架+呼吸微动画）   ← 即时出现，不等后端
  ↓ [首个 trace_event/tool_call 到达]
thinking（思考流·默认折叠摘要）         ← reasoning_stream 驱动
  ↓ [tool_call 的 subagentType === writing]
writing（写作中·字数进度+动态文案）     ← chapter_index/word_count 驱动
  ↓ [interrupt 事件]
asking（HITL 提问·中性清晰）           ← awaitingInput 驱动
  ↓ [resume] → 回到 thinking/writing
  ↓ [final 事件]
delivering（交付仪式·庆祝）             ← completed 驱动
  ↓ [error/stop]
failed / stopped（失败/停止·拟人歉意）   ← error/abort 驱动
```

**阶段切换判定逻辑**：
- `booting → thinking`：收到第一个 `trace_event`（run_start）或 `tool_call`
- `thinking → writing`：收到 `tool_call` 且 `subagentType === "writing"`（或 agent_name 含 writing-subagent）
- `writing → thinking`：writing task 结束后下一个 task 不是 writing（回到大纲/构建）
- `* → asking`：收到 `interrupt` 事件
- `* → delivering`：收到 `final` 事件
- `* → failed/stopped`：error/abort

**非 writing 阶段（storybuilding/detail-outline/general）的表达**：
- 纯动态文案轮播 + 呼吸动画，不显示字数进度。
- 构建阶段用轮次表达（"故事构建·第 2 轮"）。
- 这些阶段在 thinking 态内消化，不单独成态。

### 阶段命名方案 —— 动词短语

| 技术名（StageType） | 人话名（用户可见） |
|---|---|
| storybuilding | 构思故事 |
| detail-outline | 规划章节 |
| writing | 动笔写作 |
| general | 收尾整理 |

## 数据模型设计（第 3 轮确认）

### ChatMessage 扩展

`executionPhase` 存在 message 上（简单直接，历史一致性天然）：

```typescript
type ExecutionPhase =
  | "idle"        // 待机
  | "booting"     // 黑屏期·优雅骨架+微动画（即时出现）
  | "thinking"    // 思考流·默认折叠摘要
  | "writing"     // 写作中·字数进度+动态文案
  | "asking"      // HITL 提问·中性清晰
  | "delivering"  // 交付仪式·庆祝
  | "failed"      // 失败·拟人歉意
  | "stopped";    // 停止·拟人歉意

type ChatMessage = {
  role: "assistant" | "user";
  content: string;
  tools?: ToolStatus[];
  contentFormat?: "text" | "markdown";
  traceId?: string;
  status?: "streaming" | "completed" | "failed" | "stopped";  // 保留（向后兼容 trace 面板等）
  // ── 新增 ──
  executionPhase?: ExecutionPhase;   // 体验阶段（驱动 ExecutionView 子视图）
  awaitingInput?: { ... };           // 保留（HITL）
};
```

**注意**：`status` 和 `executionPhase` 并存。`status` 是消息级生命周期（供 trace 面板/历史判断），`executionPhase` 是体验级阶段（供 ExecutionView 渲染）。两者有映射关系（completed→delivering, failed→failed, stopped→stopped）但不完全等价（booting/thinking/writing/asking 都是 streaming 的子态）。

### 思考流数据 = 仅瞬态，不持久化

- `reasoning` 文本只存在 `executionStore` 的瞬态状态里（`activeReasoning: string`），**不写入 message**。
- 切会话回来时，已完成的 message 只显示 `executionPhase: "delivering"` 的结果，不重播思考流。
- 符合需求"只留结果，折叠过程"。

### 后端 reasoning_stream 事件契约（P2）

新增独立 SSE 事件，与 `model_stream` 平行：

```
event: reasoning_stream
data: {"content": "嗯，让我想想第3章的情节走向..."}
```

- 前端按事件类型分流：`reasoning_stream` → 思考流 UI（折叠摘要），`model_stream` → 正文。
- 后端改造点：`events.py:222-231` 的 `on_chat_model_stream` 分支，读 `chunk.additional_kwargs["reasoning_content"]` 并转发。
- DeepSeek thinking 模式下，reasoning 和 output 是**先后**产出的（先 reasoning 完再 output），前端需处理这个时序。

## Zustand Store 架构（第 4 轮确认）

### 四 Store 分离

```
stores/
  execution.ts   ← SSE消费/executionPhase/messages/思考流瞬态/停止重试
  workspace.ts   ← 工作区/会话/风格CRUD
  trace.ts       ← trace列表/详情/历史回放
  content.ts     ← 面板数据(大纲/人物/细纲/世界观/正文)轮询
```

home.tsx → 瘦成纯编排壳（目标 <200 行），从各 store 取数据传给组件。

### executionStore 内部结构

```typescript
interface ExecutionStore {
  // ── 持久态（写 message，切会话保留）──
  messages: ChatMessage[];
  threadMessages: Map<string, ChatMessage[]>;  // 会话切换存取（替代 threadMessagesRef）

  // ── 瞬态（仅运行中，不持久）──
  activeReasoning: string;       // reasoning_stream 累积（不写 message）
  activeTraceId: string;         // 当前活跃 trace
  streamedText: string;          // model_stream 累积（RAF 同步到 message）
  loading: boolean;

  // ── 编排 actions ──
  submit(prompt: string): Promise<void>;
  resume(text: string): Promise<void>;
  stop(): void;
  retry(): void;

  // ── 会话管理 ──
  switchThread(threadId: string): void;  // 存当前消息、加载目标消息
  clearMessages(): void;

  // ── 内部（SSE 消费）──
  handleStreamEvent(event: StreamEvent): void;  // 从 performSubmit 抽出的事件分发
  derivePhase(event: StreamEvent, current: ExecutionPhase): ExecutionPhase;  // phase 派生
}
```

### 高频更新策略 = RAF 批量同步

- `streamedText` / `activeReasoning` 只在**瞬态变量**累积（不触发渲染）。
- 用 `requestAnimationFrame` 批量同步到 `message.content` / 思考流 UI（最多 60fps）。
- 解决 model_stream/reasoning_stream 每秒几十个 chunk 的重渲染问题。
- 实现要点：store 内部维护一个 rafId，stream chunk 写瞬态变量，RAF 回调统一 flush 到 message。

### StageFlowView / StageTrail 去留 = 保留逻辑废组件

- **保留**：`stage.ts` 的 `projectStageFlow` 派生逻辑（供 ExecutionView 内部的阶段进度/焦点文案用）。
- **废弃**：`StageFlowView.tsx`、`StageTrail.tsx` 组件（由 ExecutionView 内的新子组件替代）。
- 旧 `.tool-status` 死代码 CSS（`globals.css:660-728`）一并清理。

## ExecutionView 子视图 UI 规格（第 6 轮确认）

### 视觉系统基线（复用现有）
- 主色：`--teal`（青绿，完成态）、`--coral`（珊瑚，温暖/交付）、`--gold`（金色，点缀）
- 底色：`--bg #efe3c8`（米黄暖底）、字色 `--ink #2e2618`（深棕）
- 动画体系：`stage-pulse`（1.2s 透明度脉动）、`stage-current-glow`（1.8s 光晕）、`stage-focus-breathe`（1.8s 呼吸）
- 暗色模式：`--bg #1a1714`、`--ink #e8e2d6`、`--teal #6ecfb8`

### ExecutionView 容器结构
```
<article class="message assistant" data-phase={executionPhase}>
  <span class="message-role">小衍</span>           ← 角色标签从"Agent"改为"小衍"
  <ExecutionView phase={executionPhase} ... />      ← 按 phase 切换子视图
  <MessageContent content={content} />              ← 正文（markdown）
```

### 各子视图规格

#### T9 BootingView（booting 态·黑屏期）
**触发**：用户按发送的瞬间（不等后端事件）。
**目的**：消除"发送后空荡"的焦虑，即时反馈。
```
┌─────────────────────────────────┐
│  ◎ 小衍 · 准备中                │   ← 拟人头像点(◎) + "准备中"文案
│  ◉◉◉ (呼吸/波纹动画)            │   ← 三点呼吸动画（非 spinner）
└─────────────────────────────────┘
```
- **视觉**：小衍头像图标（圆形，`--teal` 描边）+ "准备中"文案 + 三点呼吸波纹动画（非传统 spinner，用 `stage-focus-breathe` 变体）。
- **动画**：头像轻微缩放呼吸（0.95↔1.0），三点波浪式依次亮灭。
- **退出**：首个 `trace_event`/`tool_call` 到达 → 淡出（150ms）→ 切 thinking/writing。
- **P1 降级**：reasoning 未接入时，booting 直接过渡到 writing/thinking（无思考流）。

#### T10 ThinkingStream（thinking 态·思考流折叠摘要）
**触发**：收到 `trace_event`（run_start）且未进入 writing 阶段。P2 后 `reasoning_stream` 驱动。
**目的**：让用户看到小衍"在想什么"，但默认不吵。
```
┌─────────────────────────────────┐
│  ✍️ 小衍正在构思故事的框架...   │   ← 折叠摘要（拟人化一行）
│                        [▾ 展开] │   ← 可展开看原始 reasoning
│  ── 展开后（P2）──              │
│  让我想想，主角在这里应该...     │   ← reasoning_stream 原文
│  考虑到前两章的节奏...          │
└─────────────────────────────────┘
```
- **折叠态**（默认）：拟人化摘要一行 + 脉动圆点（`stage-pulse`）。摘要文案由 phase + stage 推断（"正在构思故事的框架..."/"正在梳理章节脉络..."）。
- **展开态**：原始 reasoning 文本（P2 接 `activeReasoning`），等宽字体，限制高度可滚动。
- **P1 占位**：reasoning 未接入时，折叠态只显示推断摘要（无展开），呼吸动画。
- **保护**：展开态不暴露工具名/技术术语（reasoning 原文里可能有，但折叠态一定是人话）。

#### T11 WritingProgress（writing 态·字数进度+动态文案）
**触发**：`tool_call` 的 `subagentType === "writing"`。
**目的**：信息丰富化的核心——让用户持续看到进展。
```
┌─────────────────────────────────┐
│  ✍️ 好嘞，开写第 3 章啦！       │   ← 动态文案（活泼陪伴，轮播）
│                                 │
│  第 3 / 10 章                   │   ← 章节进度（total_chapters）
│  已写约 1,240 字                │   ← 实时字数（word_count）
│  ████████░░░░░░░░░░░ 30%       │   ← 字数进度条（按目标字数或均字数）
│                                 │
│  构思 ✓  规划 ✓  ●写作 ○收尾   │   ← 阶段缩略链（复用 stage trail 逻辑）
└─────────────────────────────────┘
```
- **动态文案轮播**：活泼陪伴调性，每 5-8s 轮播（"好嘞，开写第 3 章啦！"/"嗯，这章我想让主角..."/"写到这里节奏不错..."），来自文案库。
- **字数进度条**：横向填充条，按"目标字数"或"单章均字数（如 3000）"计算百分比。不确定时不显示百分比，只显示已写字数。
- **阶段缩略链**：复用 `stage.ts` 的 stage 数据 + StageTrail 的视觉逻辑（但用新组件渲染），已完成 `✓`、当前 `●`（脉动）、未开始 `○`。
- **脉动动画**：进度条填充时有轻微脉动，表示"活着"。

#### T12 AskingView（asking 态·HITL 中性提问）
**触发**：`interrupt` 事件。
**目的**：清晰高效，让用户快速做决策。
```
┌─────────────────────────────────┐
│  小衍：这里需要你拍个板——       │   ← 引导语（中性，一句）
│                                 │
│  第 3 章主角是否遇到反派？       │   ← 问题（清晰）
│  ○ 遇到，加些冲突               │   ← 选项（人话，非"选项A"）
│  ○ 先铺垫情绪，下章再遇         │
│  ○ 你决定就好                    │
│  [提交选择]                      │
└─────────────────────────────────┘
```
- 复用 `InterviewOptions`（choice）和 `ImageReviewCard`（image_review），外层包小衍引导语。
- 选项标签去技术化（来自后端 `AskUserOption.label`，已是人话格式）。
- 提交后 `asking` → `thinking`/`writing`（恢复执行）。

#### T13 DeliveryCeremony（delivering 态·交付仪式）
**触发**：`final` 事件 → message.executionPhase = "delivering"。
**目的**：制造成就感峰值。
```
┌─────────────────────────────────┐
│  ✨ 小衍写完啦！                │   ← 交稿语（庆祝）
│                                 │
│  本次产出：第 3 章 · 3,200 字   │   ← 结果摘要
│  耗时 4 分 12 秒                │
│                                 │
│  [正文已展示在上方]              │
│  「你觉得怎么样？要改跟我说」   │   ← 收尾互动语
└─────────────────────────────────┘
```
- **入场动画**：`✨` 粒子效果或淡入放大（200ms），`--coral`/`--gold` 暖色调。
- **结果摘要**：从 finalData + stageFlow 派生（产出章节/字数/总耗时）。
- **收尾互动语**：活泼陪伴调性，来自文案库。
- **正文位置**：正文（MessageContent）在 ExecutionView 上方，交付卡片在正文下方收尾。

#### T14 FailedView / StoppedView（failed/stopped 态·拟人化歉意）
**触发**：error/abort → message.executionPhase = "failed"/"stopped"。
```
┌─────────────────────────────────┐
│  failed:                        │
│  抱歉，刚才出了点问题...         │   ← 拟人化歉意
│  （原因用人话：连接断了/积分不足）│
│  [↻ 再试一次]                   │   ← 重试按钮
│                                 │
│  stopped:                       │
│  好的，停下了。要继续的话...     │   ← 拟人化
│  [↻ 继续]                       │
└─────────────────────────────────┘
```
- 错误原因翻译成人话（HEARTBEAT_TIMEOUT→"连接好像断了"/403→"积分不够了"/其他→"出了点小问题"）。
- 重试按钮保留现有功能（`handleRetry`）。

#### T19 历史消息折叠（历史回看）
**触发**：切到非当前活跃的 message（历史 message）。
```
┌─────────────────────────────────┐
│  小衍                           │
│  [正文内容...（最终结果）]       │   ← 只留正文
│                                 │
│  [▾ 查看执行过程]               │   ← 可展开折叠
│  ── 展开后 ──                   │
│  构思 → 规划 → 写作 → 收尾      │   ← 阶段摘要（复用 stage.ts）
│  耗时 4m12s · 3,200 字          │
└─────────────────────────────────┘
```
- 历史 message 的 executionPhase 显示为 delivered（结果态），不重播思考流/动态文案。
- 可展开"执行过程"折叠区：阶段缩略链 + 耗时/字数摘要（复用 stage.ts 派生）。
- 思考流不持久化，历史回看不显示。
