# harness 版本系统升级 · 需求基准

## 核心诉求（待用户确认）

> 升级进化端 harness 的版本管理机制。当前存在 git 割裂问题且机制过于复杂，
> 希望借鉴业界工程实践重新设计一套**清晰分明**的 git 版本管理机制。
> 涉及决策：进化后的 harness 存放位置、回溯方式、版本管理、一致性/安全性/可靠性、架构清晰度。

## 现状梳理（调研得出，非用户陈述）

### 当前三层机制

```
层 1 git 层（源码物理存储）
  evolution/harnesses/current/ = evolution 的工作目录（独立 git 仓库）
    .git/ → remote origin → harness.git (bare repo)
  executor 侧：pull_production() clone bare repo；checkout_commit(hash) clone 指定 commit

层 2 config 快照层（逻辑配置存储）
  SQLite harness_snapshots 表
    version | parent_version | config_json | source_commit | status | change_summary | source_session
  publish_config(): bootstrap 读盘 → 生成 config_json → 存库 + 旧 production 降 retired

层 3 version_changes 层（差异展示）
  prompt diff / skills diff / processor diff / intent
```

### 关键流程

- **publish**：git commit_and_push 拿 source_commit → bootstrap 读盘生成 config_json → publish_config 存库 → notify_executor
- **discard**：取当前 production 的 source_commit → git reset --hard working tree → 推进状态
- **executor 同步**：HTTP 通知（fire-and-forget 降级）→ 进程级缓存 + reload

### 已识别的潜在"割裂"点（待用户确认哪些是真痛点）

1. 主仓库 vs 子仓库 git 嵌套：harnesses/current/.git 独立，但目录在主仓库内
2. config_json 与 source_commit 两套"真相源"，分两步写入，可能不一致
3. discard 用 git reset --hard，破坏性且不区分多 session 交织
4. executor 靠 HTTP 通知拉取，无强一致保证
