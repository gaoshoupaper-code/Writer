# 需求：积分制度设计 + 进化端账号/邀请码/额度管理

## 核心诉求（已确认）

> 在进化端建立一套**平台级积分计费体系**：用户创作消耗积分，用积分替代"API 额度"概念。同时配套在进化端做**用户账号/密码、邀请码、额度**的管理后台（仅超级管理员可见）。深层诉求：利用积分制半透明特性，在未来 API 成本上涨时拥有暗调灵活性，同时用户无法察觉。

## 现状摸底（代码探索事实，2026-07-09）

### 1. 认证体系：已有"邀请码 + 账号密码"双因素，非纯邀请码
- 注册：`{邀请码 + 用户名 + 密码}`，邀请码校验通过后建账号（存 bcrypt 哈希密码）。
- 登录：纯账号密码，不再要邀请码。`executor/app/auth/__init__.py:152-171`
- Session：HttpOnly cookie，30 天滚动续期。evolution 复用同一 cookie 做 SSO。

### 2. 邀请码：一次性、不带任何额度字段
- `invite_codes` 表（`executor/app/platform/core/db/__init__.py:77-85`）字段：code / created_by / used_by / is_admin_code / created_at / used_at / revoked_at。
- **没有任何 quota/credits 字段**。唯一特殊属性是 `is_admin_code`（注册即管理员）。
- 注册时用户拿到的 `workspace_quota`（作品数上限，默认5）来自全局配置，与邀请码无关。

### 3. "额度"真相：只有 workspace_quota（作品数量上限），且未强制校验
- `users.workspace_quota INTEGER DEFAULT 5` —— 唯一的"额度"字段。
- **重大缺口**：全仓库没有任何 `>= workspace_quota` 的拦截判断。`create_workspace`（`thread_store.py:56-63`）只查 title 非空，不查数量是否超额。即：配额只展示不拦截。
- 前端 `desktop/src/pages/settings.tsx:257` 显示"作品配额：x / y"。

### 4. API 调用成本：平台不承担，用户自带 key
- 每次写作调用读 `users.get_api_key_plain(owner_id)`（用户自己填的 LLM key，AES-256-GCM 加密存储）。
- 用用户自己的 key 调外部 LLM（deepseek/glm 等）。**平台不代计费、不扣点。**
- 即：当前"API 额度"= 用户自己 key 的余额，平台完全不参与。

### 5. 进化端前端：管理后台页面为零
- 技术栈：Next.js 15 + React 19 + Tailwind 4 + Radix UI。
- executor 已建好 `/api/admin/*` 接口（邀请码 CRUD、用户管理 list/禁用/重置密码、profile）。
- **但 evolution 前端一个管理页都没有**（TopNav 无 admin/邀请码/用户入口）。`scripts/manage.py` 注释证实 admin 后台 UI 曾被砍。
- evolution 鉴权：SSO 借 executor session + `ALLOWED_USER_IDS` 白名单。

### 6. 完全不存在的概念
- API 调用额度/扣减、积分/credits/余额、充值/扣费、积分流水账 —— 全部从零。

## 已确认决策

### D1【商业模式】✅ 平台代付转型（2026-07-09 确认）
- 平台统一提供 API key，用户花积分创作。
- 用户不再需要自己填 API key（现有 `encrypted_api_key` 机制将作为过渡/可选保留，待定）。
- 积分 = 平台定价权 + 成本对冲工具。
- 隐含：平台要扛 LLM 成本、要做风控（防薅羊毛/防滥用）。
- 转型路径（渐进 or 一步到位）待澄清。

### D2【透明度】✅ 半透明（业界主流）（2026-07-09 确认）
- 积分可充值（如 ¥10 = N 积分），但不标明"1积分 = ?token"。
- 换算率藏在后台，用户知道花了几块钱，但算不出后台毛利。
- 暗调空间中等，被识破风险中等。
- 对应业界：GitHub Copilot 的 "AI Credits"（与美元脱钩的虚拟单位）路线。

## 待澄清（动态关注面追踪）

- [ ] **积分锚点**：见下方"锚点分析"专节（已排除"动作计费"）
  - **用户约束（2026-07-09 确认）**：锚点必须**抗系统进化**——创作系统是进化型，子代理/动作会不断拆分变化，锚点不能绑定在"具体动作"上，否则每次系统进化都要重新定价，且新旧账目无法对齐。
  - 据此排除方案：纯"动作计费"（动作会变，不稳定）。
  - 候选稳定量：token（消耗维度）、字数（产出维度）——两者都是比"动作"更底层、不受系统进化影响的不变量。
  - **二次筛选**：字数有盲区（thinking模型思考耗token不产字；大纲/审查产出非正文字数；设定文档算不算？）。**token 是唯一"抗进化 + 零盲区"双绿的锚点。**

### D3（推荐待确认）：积分锚点 = **token 实扣（事后结算）**
- **计费依据**：按每次创作的真实 token 消耗 × 后台单价折算积分，事后结算。
- **用户感知**：永远只看"积分余额"，看不到 token；token 是后台齿轮。
- **配置表**：仅需 `模型 → 积分/千token` 一张表。系统进化时零配置成本（新子代理自动按实际消耗计费）。
- **暗调机制**：调"token→积分"换算率（后台变量）。因 token 消耗本身每次波动，用户无法建立稳定锚定，暗调淹没在噪声中，感知度极低。
- **可预测性弱点**：用户无法预测单次花费 → 靠"余额管理 + 单次速率上限（防失控）"补偿。
- **业界印证**：Cursor / Copilot / Sudowrite新版 本质都是 token-based credits。Sudowrite 从"字数制"转向此模型正是因为成本吸收能力。

**待用户确认后，下一步细化**：初始定价（积分/千token）、充值汇率（¥?=多少分）、单次速率上限值。

### D3 ✅ 已确认（2026-07-09）：积分锚点 = token 实扣（事后结算）
- 计费依据：按每次创作的真实 token 消耗 × 后台单价折算积分。
- 用户感知：永远只看"积分余额"，看不到 token。
- 配置表：仅需 `模型 → 积分/千token` 一张表。
- 暗调旋钮：调换算率，淹没在 token 波动噪声中。

### D4 ✅ 已确认（2026-07-09）：事前预扣 + 多退少补
- 创作前按"预估消耗"先冻结一批积分（预扣）。
- 跑完按实际 token 消耗结算：多的退回，少的补扣。
- 需要为不同创作规模设定"预扣上限"（防单次失控）。

### D5 ✅ 已确认（2026-07-09）：失败/中断的 token 全算（用户承担）
- 用户补充的关键业务事实：**系统支持断点续创，内容落盘不丢失**。用户中断后，下次创作能看到之前内容接着写。
- 因此"全算"合理：即使中断，用户已获得中间产物（落盘的章节/大纲），且可续创，token 消耗对应了真实获得的价值。
- 风险点（待关注）：系统自身崩溃（非用户主动停止）导致的中断——当前规则也是全算，用户是否接受"平台挂了还扣我分"？暂记录为待观察项。

## 成本真相（2026-07-09 基于 deepseek 实际定价计算）

### D6 输入：模型实际定价（deepseek）
| 类型 | 价格（¥/百万token） | 相对倍数 |
|---|---|---|
| 输入-缓存命中 | ¥0.025 | 1× |
| 输入-缓存未命中 | ¥3 | **120×** |
| 输出 | ¥6 | **240×** |

> ⚠️ 极端价差：同样的 1000 token，缓存命中输入 ¥0.000025，输出 ¥0.006 —— **差 240 倍**。

### 成本测算（估算值，需上线后用真实数据校准）
| 创作规模 | 平台 deepseek 成本（估） |
|---|---|
| 写 1 章（~1000字正文+thinking+审查） | ≈ ¥0.06–0.10 |
| 写 1 篇短文 | ≈ ¥0.10–0.20 |
| 写 1 本 20 章小说（含storybuilding迭代+细纲+逐章+审查） | ≈ ¥3–4 |

### D7 ✅：token 折算方式（三档权重）
因 240 倍价差，token 实扣**不能统一计价**，必须折算：
- 输出 token × 2.0 权重
- 输入缓存未命中 × 1.0 权重（基准）
- 输入缓存命中 × 0.01 权重
→ 折算成"标准 token"后统一按积分单价计费。
（折算权重本身也是暗调旋钮。）

### D27 ✅（2026-07-09）：负数控制 = 全局固定负债上限
- 所有用户最多扣到 **-5000 分**（≈¥5 成本，初始值，上线后可调）。

### D28 ✅（2026-07-09）：超级管理员标识 = 新增 is_super_admin 字段
- `users` 表新增 `is_super_admin INTEGER NOT NULL DEFAULT 0`。
- 只有 `is_super_admin=1` 的用户能访问进化端管理后台（账号/邀请码/积分/流水管理）。
- 与 `is_admin` 区分：`is_admin=1` 是普通管理员（可发邀请码等），`is_super_admin=1` 是超级管理员（唯一，只有你）。
- 超级管理员初始创建：沿用现有 bootstrap 机制（首启动按 .env 建管理员时，同时置 is_super_admin=1）。
