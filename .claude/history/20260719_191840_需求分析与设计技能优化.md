# 需求分析与设计技能优化

## 核心诉求

优化现有两个工作流技能（`require` 需求分析、`design` 设计），目标是：
- 让 require 既能保持"只管 WHAT/WHY"的职责边界，又不会在分析时想当然——尤其在那些**最终会卡死 design 的实现性问题上**提前暴露风险。
- 让 design 在产出技术细节的同时，让**非技术/半技术用户也能真正参与决策**——而不是只能盲点"推荐"。

**判断：本质不是"合并与否"的问题，而是"两个技能接缝处断裂"的问题。** WHAT/HOW 的职责分离是业界共识（PRD vs Design Doc），不应合并；但接缝处的衔接机制当前是空的。

## 当前认知（待用户校准）

| 维度 | require 现状 | design 现状 |
|---|---|---|
| **定位** | 只问 WHAT/WHY，不碰 HOW | 只管 HOW，输入需求 |
| **优点** | 实用，把模糊点炸出来 | 能看到实现细节 |
| **痛点** | 不验证可行性，可能"想当然"地接受一个落地有坑的需求 | 选项都是技术维度，用户看不懂利弊，只能点"推荐" |
| **接缝断层** | 产出物里没有"实现风险提示"——只冻结 WHAT，不知道哪些 WHAT 在 HOW 层会塌 | 输入时不做需求完整性探测，遇到断层只能建议退回 require |

## 业界参考范式（待用户选择采纳哪几个）

| 范式 | 出处 | 核心机制 | 对我们的启发 |
|---|---|---|---|
| **Working Backwards (6-pager)** | Amazon | 从最终用户视角倒写新闻稿，再回推 PR/Design | 强制 require 用"用户能感知的场景"而非抽象维度 |
| **Design Doc / RFC + Alternatives Considered** | Google | 每个决策点必须写"备选方案 + 否决理由" | design 的选项要写"否决的业务理由"，不止利弊 |
| **Spec-Driven Dev** | 测试先行 | WHAT 用可执行的验收标准锚定 | require 输出"验收用例"，自动验真伪 |
| **Event Storming** | DDD | 用具体事件穿越系统，而非抽象维度 | require 改用"具体场景穿越"代替维度清单 |
| **ADR (Architecture Decision Record)** | ThoughtWorks | 每个架构决策独立成卡，含上下文+后果 | design 的每个决策落纸时带"业务后果"段 |
| **Claude Code / Cursor 的 Plan Mode** | 业界 Agent 工程 | 计划-确认-执行三段式，计划阶段可见可改 | 整体工作流的"人在回路"强化 |

## 已冻结决策（R1 共识）

- [x] **不合并**。WHAT/HOW 职责分离是业界共识，保持。
- [x] **design 痛点根因**：用户"看不懂术语"+"其实想学习"——不是信息不足，是**信息维度错配**。正解是**双层呈现**：业务后果层（决策用）+ 技术细节层（学习用），不能二选一。
- [x] **require 治法**：加**可行性快检**——不动核心机制（仍只管 WHAT/WHY），只加一道"在现有系统里成不成立"的轻量闸门。
- [x] **接缝机制**：**双向咬合**。require 产出端带"实现风险清单"；design 输入端做完整性体检，发现断层退回 require。两个技能各加一段"接缝协议"。

## 已冻结决策（R2 共识）

- [x] **design 双层呈现形态**：**选项内双段**。每个选项内部分两段——【决策层·人话】讲业务后果；【学习层·供你学】讲方案细节，术语首次出现给一句通俗解释。结构固定、易扫描。
- [x] **可行性快检颗粒度**：**关键决策触发**。每冻结一个关键决策点（不是每条小需求）就跑一次快检，往风险清单补一条。
- [x] **接缝协议载体**：**文档内固定段落** `§ 实现风险清单`。每条含「风险点 + 在哪塌 + 建议验证方式」。design 读取时直接扫这个段落。

## 已冻结决策（R3 共识）

- [x] **design 决策层覆盖维度**：固定 3 个——**时间成本 / 扩展阻力 / 用户体感**。（不选"维护负担"：单人项目意义不大；不多选：避免每个选项过长。）
- [x] **可行性快检范围**：**固定 checklist**（座底，AI 可补需求特有项）。具体清单见下方"§ 快检 checklist 候选"。
- [x] **验证方式**：**下一个真实需求试跑**。技能改完后不立即做历史回归，而是在下一个真实需求上边用边调。（用户选择，偏离 AI 推荐但合理——技能优化非代码重构，试跑反馈更自然。）

## § 快检 checklist（最终定稿）

基于 MEMORY 偏好"全要素枚举"+ 业界设计断层高发区，**8 项座底**，AI 可按需求动态追加：

| # | 检查项 | 问什么 |
|---|---|---|
| 1 | **数据结构** | 现有数据模型能支撑这个需求吗？要不要新增字段/表/快照？ |
| 2 | **外部依赖** | 依赖了哪些外部系统/服务/API？它们稳定吗？挂了怎么办？ |
| 3 | **状态机** | 涉及的状态流转完整吗？有没有漏掉中间态/异常态？ |
| 4 | **并发与竞态** | 多用户/多进程同时操作会冲突吗？需要锁/幂等吗？ |
| 5 | **错误路径** | 失败了怎么恢复？部分成功怎么处理？用户能看到什么？ |
| 6 | **权限与边界** | 谁能做这个操作？跨用户/跨租户会不会越权？ |
| 7 | **性能与规模** | 数据量上去后会塌吗？有没有 N+1 / 全表扫描 / 内存泄漏风险？ |
| 8 | **部署与配置** | 上线需要改部署/配置/迁移吗？有没有破坏性变更？ |

> **使用规则**：require 跑快检时逐项扫，不适用的标 `N/A · <原因>`。具体需求暴露的新维度，AI 动态追加并注明"需求特有项"。

## 交付给 design 阶段的"实现风险清单"

> 这是本次需求自身的实现风险——design 推演时必须消费。

| # | 风险点 | 在哪塌 | 建议验证方式 |
|---|---|---|---|
| R1 | **两个技能改动后可能影响现有 `.claude/md/` 历史文档的兼容性** | 如果在 frontmatter 加新字段或段落格式变了，旧文档可能扫不到 | design 阶段确认：新段落只增不改旧结构，旧文档可被新版 design 当作"无风险清单"正常消费 |
| R2 | **8 项 checklist 可能过重，让 require 节奏变慢** | 关键决策触发后跑 8 项快检，可能让一轮对话变长 | design 阶段定颗粒度：快检只输出"有风险/无风险"二值，详细分析留 design；或允许批量快检（多个决策合一次） |
| R3 | **双层呈现可能让 design 选项长度翻倍** | 每个选项 2 段（决策层 + 学习层），3 个选项就是 6 段，用户扫描负担 | design 阶段定排版规则：决策层用表格压缩，学习层用折叠/缩进区分主次 |
| R4 | **`§ 实现风险清单` 段落标识要唯一且机器可识别** | design Step 0 要扫这个段落，标识不统一就扫不到 | design 阶段定标识规范：固定标题字符串 + YAML 锚点双保险 |
| R5 | **MEMORY 同步是事后的，可能被忘** | 设计阶段忙起来忘了更新 MEMORY | design 收尾自检清单加一条："本次是否触发了 MEMORY 更新？" |
