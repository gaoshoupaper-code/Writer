# 重构 harness 版本系统

## 核心诉求

**一句话**：把 harness 版本管理从"4 个 git 仓库 + DB 双轨割裂"重构为"单一真相源 + 清晰分层"，让版本流转可追溯、可回滚、认知负担低。

### 当前病灶（调研已定位）

1. **4 个 git 仓库并存，互相割裂**：
   - `./.git`（主仓库）
   - `evolution/harness.git/`（bare repo，但非 bare，有 working tree）
   - `evolution/harnesses/current/.git`（工作副本，remote 指向主项目 GitHub）
   - `.harness_checkout/production/.git` + `.harness_checkout/harness_xxx/.git`（临时副本）
   - `harnesses/current` HEAD（`bc70058`）与 `production` checkout HEAD（`2782f1c`）**不一致**

2. **DB + git 双轨**：`harness_snapshots` 表存 `config_json` + `source_commit`，同一版本有 3 个可能矛盾的真相源

3. **生产路径未接 config 驱动**：执行端 `pkg.assemble(ctx)` 没传 config——config_json 写了但生产没用

## 调研结论（已确认方向）

- harness 配置（prompts/middleware/skills）本质是**数据**，应走 DB registry
- git 只管源码（executor 自己的代码）
- 业界分层：进化引擎层 → 版本注册表层（不可变） → 发布回滚层（label 指针）

## 已确认事实（第一轮挖掘）

### 事实 1：harness 是「全要素进化」——源码级进化

evolve agent 的写工具（`writers.py`）能改的不只是 prompt 文本，还包括：
- `write_middleware` → 新建 middleware `.py` 源码
- `write_tool` → 新建 tool `.py` 源码
- `write_subagent` → 新建 subagent `.py` 源码
- `edit_source` → **修改任意已有文件**（含所有 .py 源码）

**结论**：harness 的"完整版本"包含**源码文件**，不只是 config_json。
纯 DB（config_json）**无法**成为唯一真相源——因为 config 只存了类名引用和 prompt 文本，
真正的 middleware/tool/subagent 的 .py 代码不在 config 里，在文件系统/git 里。

### 事实 2：进化产物落盘在 harnesses/current/

evolve agent 的 FilesystemBackend root_dir = `harnesses/current/`，
所有改动直接写进这个目录。然后通过 git commit → push 到 bare repo → executor pull。

### 由此推导的版本真相源

一个 harness "完整版本" = **一组文件的状态快照**（prompts/*.md + middleware/*.py + tools/*.py
+ skills/** + subagents/** + manifest.json + __init__.py）

这组文件需要被版本化。问题是：用什么机制版本化这组文件？

### 事实 3：生产路径确实没接 config 驱动——Phase 8 渐进迁移未完成

代码证据（`agent.py:170-171`）：
```python
pkg = load_current_package()
return pkg.assemble(ctx)  # ← 没传 config！走包内硬编码（Phase 1 薄包装逻辑）
```
`load_current_package()` → `pull_production()`（git pull bare repo main）→ load_package → assemble(ctx)

**生产路径完全是 git 驱动**：pull 源码 → 跑源码里的硬编码 assemble 逻辑。config_json 只在 A/B 路径用了。
ab_endpoint 注释明确写了："生产：assemble(ctx)（无 config，硬编码）"。
→ 这是 Phase 8 渐进迁移未完成，不是有意设计。

### 事实 4：A/B 路径活着，但已部分迁移到 git checkout 模式

- `ab_runner.py`（tar 模式）= Phase 7 遗留，被 `internal.py:338` 调用
- `ab_endpoint.py`（git checkout 模式）= Phase 8 新路径，走 `checkout_commit(req.source_commit)`
- A/B 两种子模式：
  - 快照版本：`checkout_commit(source_commit)` → clone bare repo + checkout 指定 commit
  - working 包：直读 `harnesses/current/`（未提交的改动）
- A/B 路径**传 config**：`assemble(ctx, config, source_root)`——这是 config 驱动的唯一使用者

### 事实 5：bare repo 是当前版本管理的实际承载体

bare repo（`evolution/harness.git/`）的 main 分支 = 生产 harness 源码。
每个 commit = 一个版本。`source_commit` 字段 = bare repo 里的 commit hash。
执行端 pull main → 生产；checkout 指定 commit → A/B 回溯。

## 关键决策（已拍板）

### 决策 1：git 唯一载体（方案 A）

**「版本」= bare repo 的一个 git commit。**

- bare repo（`evolution/harness.git/`）的 commit = harness 版本的唯一承载体
- DB `harness_snapshots` 表角色降级为**元数据索引**：version 号、source_commit（commit hash）、
  parent_version（谱系）、change_summary、status（production/retired）、created_at
- **删除 config_json 列**（或废弃不用）——config 不再双轨存 DB
- 执行端统一靠 git pull/checkout 拿源码 → 从源码读 config（bootstrap.build_v1_config 或同等机制）
- 生产路径接上 config 驱动（当前断点修复）

**为什么选 A**：
- harness 是源码级进化（改 .py），git 是源码版本管理的天然工具
- 消除 DB config_json 与 git 源码的双轨割裂
- commit hash 天然不可变、天然有 diff、天然有谱系
- 认知负担最低：一个 commit = 一个版本，无需理解两套机制

### 决策 2：回滚 = label 重指向

回滚 = 在 DB 里把旧版本的 `status` 改回 `production`，当前 production 降 `retired`。
- 纯 DB 元数据操作，秒级、可逆
- 不创建新 commit，不改 git 历史
- 执行端下次 pull 时拿旧 commit（通过 DB 的 source_commit 定位）
- 已有的 `publish_config` 原子切换逻辑就是这个模式，沿用

### 决策 3：harnesses/current/ = bare repo 的工作区

`harnesses/current/` 保留 `.git`，但 **remote 改为指向 bare repo**（而非主项目 GitHub）。
- evolve agent 在这里改代码（FilesystemBackend root_dir 不变）
- 改完 commit + push 到 bare repo
- 它是 bare repo 的唯一工作入口，不再追主项目 origin

**消除的割裂**：当前 `harnesses/current/.git` 的 remote 指向 `gaoshoupaper-code/Writer.git`（主项目），
而 bare repo 也追同一个 origin——两条线追同一 origin 是割裂根源。改 remote 指向 bare repo 后，
单向流：current → bare repo → executor pull。
