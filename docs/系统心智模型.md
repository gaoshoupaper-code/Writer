## 图 1 · 系统总览

三端 + 外部依赖的全景。**主线（粗箭头）是一次写作生成请求的完整旅途**，
细箭头是进化闭环的回流。

**三个关键认知（看这张图记住这三点）：**

1. **executor 是绝对核心**。前端只碰它，它直连 LLM / memory.db（NWM 记忆） / writer.db。
2. **evolution 是开发与质量人员使用的幕后进化引擎**。它以一套 canonical Trace
   记录创作与内部工作负载；创作、证据编译、评估、进化各自独立 Trace，异步因果只用
   Link 和不可变制品版本关联，绝不伪造跨服务父子 Span。
3. **harness 包是连接两端的纽带**：evolution 冻结不可变 candidate；executor 从该
   exact commit 真实装配做 probe。probe 通过即晋升 production（单阶段发版——
   Harness commit、executor 装配、ArtifactSnapshotMiddleware 齐全即放行，不再要求
   snapshot trace + 证据卷宗 + 评估卷宗三件套）；reload 失败会恢复原指针并重新加载旧 production。

**客户端层有三个前端**（别混）：
- `Web 网页`（Next.js，主力）和 `桌面端`（Tauri 壳包同一套 React 组件）都调 executor
- `官网`（Astro）是纯静态下载页，**不调任何 API**

**executor 的四层架构（纵向看 subgraph）**：

| 层 | 职责 | 关键模块 |
|----|------|---------|
| **routers** | HTTP 入口，接前端 + 接 evolution | screenplay / character / threads / workspaces / internal |
| **domains** | 领域编排（writing / image） | MetaAgentService / WritingEventSink |
| **platform** | 领域无关基座 | agent / streaming / trace / credits / auth / state / memory / ... |
| **harness 包** | agent 定义（动态加载，不在 executor 仓库） | assemble / subagents / middleware / prompts / skills |

**层依赖铁律**：platform 不 import domain；domain 可 import platform；
harness 包依赖 platform.runtime 和 contracts，运行时值全由 ctx 注入。

**看这张图记两点**：
1. 写作生成不是一条直线——`MetaAgentService` 装配后，**meta agent 自主委托 5 个 subagent**
   （interview→storybuilding→detail_outline→writing），每个内部还有 review-revise 循环（详见 图 7）。
2. `WritingEventSink` 不只转 SSE——它还**在 chapter 完成时触发记忆抽取入库**（详见 图 5）。
3. **产物证据有双层保障**：Harness 的 `ArtifactSnapshotMiddleware` 贴近写工具回读正文；
   executor 的 `PlatformArtifactCaptureMiddleware` 独立兜底所有真实 creation workload，统一把
   write/edit 成功后的最终文件头记录为 ArtifactRevision。普通创作、working、snapshot、A/B、
   单次测试和 benchmark 都共享这条平台边界，证据 Agent 自身不会成为创作证据候选。

**单次测试的十秒硬终止与父进程接管（FR-002/006 / NFR-001 / CON-008）**：A/B 候选执行
（`/internal/ab/run`）在独立子进程跑（`IsolatedGenerationWorker`），父进程持有句柄。停止时：
持久 `cancel_id` + 立即标 `cancelling` → 写 `cancel_requested` 事件（取消意图不再只在内存）→
协作式 `cancel_event` → `join(10s)` → 超时 `taskkill/SIGKILL` 强杀进程。**关键修复（EVD-006/007）**：
强杀后子进程的 `_finalize_run` 不会跑，父进程 `seal_external_cancel` 接管 canonical Trace 收尾——
从磁盘重建最小活跃态、补 `run_cancelled`/`cancel_timeout` 事件、生成 manifest、收敛 integrity、
notify evolution。进程边界独立（POSIX `setsid` 建独立进程组，killpg 前校验组长身份，CON-008
不误杀父进程/同组任务）；无法确认边界时不强杀、进 `cancel_timeout`（不谎报 cancelled）。
子进程内独立构建 TraceRecorder，trace 写共享 workspace，通过 Queue 回传 trace_id。

**单次测试 trace 跨进程可发现（FR-001/004）**：子进程的 recorder 是独立内存对象，主进程
默认查不到子进程 trace（曾导致 `GET /internal/traces/{trace_id}` 稳定 404）。修复后子进程
经 IPC 一并回传 `trace_id + workspace_path`，主进程 `_execute_ab` 拿到后调
`TraceRecorder.register_external_run` 登记进主 recorder 的 `_trace_workspace` 索引；内存索引
缺失时 `find_run_by_trace_id` 退化为扫 `ab_ws_*` 临时根的磁盘兜底。evolution 发起 A/B 时
透传 W3C `traceparent` + `test_id`，对象 trace 的 `external_refs` 持久化 `test_id`/`task_id`，
使单条测试的 trace 树可跨服务追溯。

**A/B/单次测试/benchmark 接入记忆系统（NWM 记忆要素可进化闭环）**：A/B 候选执行
（`run_ab_generation`）原本只装配 model/backend/trace，**不注入记忆**——导致测试 trace 0 条
`memory_quality` 事件，进化对 6 个记忆要素"盲飞"（改完观测不到效果）。修复后 A/B 路径与生产
对齐：ctx 注入 `memory_backend`（按临时 workspace_id 隔离）+ `memory_recall_middleware_cls`
（从候选包加载，非生产缓存包），激活召回中间件 + quality_callback 埋点；stream 循环逐
super-step 扫描 `chapter/` 目录检测新完成章节，调 `trigger_chapter_ingestion`（与生产 sink
复用同一抽取触发器，DEC-002）触发逐章抽取入库。run 终态（成功/失败/取消）清理临时 memory.db，
进化复盘完全依赖 trace 的 `memory_quality` run_meta 事件（含 hits 摘要 + 抽取 stats）。
harness 检索要素（join_rules/packet_formatter）每次 assemble 按当前候选包版本注入，不再用
进程级"只注入一次"单例锁死（FR-003：同进程热加载多版本时每版本装配自身要素）。

**本次改动的关键机制（FR-006/007, CON-003, FR-005）**：
1. **取消状态单调 + 四维正交（DEC-008）**：`_sync_manual_test_status` 把 cancelled trace 映射为
   `mark_cancelled`（不再 mark_failed），cancel_timeout/interrupted 映射为 failed（可诊断技术故障）。
   终态单调保护（`is_terminal`）：已终态的记录不被迟到摄入覆写。业务状态、trace 阶段、完整性、
   取消时间线拆成正交四维；停止统一为「持久 cancel_id + 立即 cancelling → 后台 10s 真实停止确认 →
   cancelled/cancel_timeout」（超时不谎报 cancelled，CON-003）。
2. **版本显式绑定与单阶段发布**：发布时把 Harness 源码冻结为 candidate commit，
   让 executor 在该 commit 干净 checkout 做 probe 装配；probe 通过（Harness commit、装配成功、
   ArtifactSnapshotMiddleware 齐全 + identity 稳定）即移动 production。executor 始终从 registry
   解析 exact `commit_hash`，不盲跟 bare `main`；reload 返回的实际 commit/runtime identity 必须与
   probe 一致，失败立即恢复原 production。（旧两阶段门禁要求 snapshot trace + 证据/评估卷宗三件套，
   历史上从未通过过，导致 session 永远卡 pending_review，已废弃。）
3. **Harness 要素投影**：`elements_api` 只静态解析目标 commit，不执行历史代码；Middleware
   视图按真实装配顺序覆盖主控、5 个直系子代理和 3 个 reviewer，并支持单实例跨多个 hook。
4. **严格 ready 门禁**：所有下游（评估/进化/卷宗编纂）只接受 `ready`/`sealed` 卷宗，
   `_CONSUMABLE_STATUSES` 不再含 partial。取消来源 ready 卷宗须人工显式确认才进下游。
5. **零用户计费**：单次测试/卷宗/评估/进化四类工作负载不注入 CreditsService，usage 只进
   Trace 与平台成本诊断。

**看这张图记两点**：
1. **摄入和进化是解耦的**——摄入只记录事实、receipt 和完整性，不触发评估。完整性是正交维度（DEC-008）：`pending`（记录/封存中）是中性态不误报损坏；`incomplete`、`conflict`、`legacy` 只能展示，不能被卷宗、评估或进化消费；只有 `verified` 放行。创建端始终 fail-open 并显式标记 `trace_incomplete`（pending 不触发该标记）。
2. **跨服务不伪造父子 Span**：创作、卷宗、评估、进化分别是根 Trace；同步 Tool/Subagent 留在当前 Trace，异步流程由 Span Link、来源 Trace 和不可变制品版本双向还原。
3. **发版闭环**：evolve 产改动 → candidate committed → probe 装配通过 →
   registry_promoted → executor_refresh_ack → activated。单阶段：probe 是唯一门禁，
   通过即晋升；失败和回滚都是追加事实，进程重启会按 source_session 恢复同一版本，不重复造 candidate。

## 图 5 · memory 闭环 — NWM 叙事学类型化记忆（executor 进程内自洽）

1. **不依赖 Graphiti/FalkorDB**。记忆是自研 NWM——SQLite 存 typed records，sqlite-vec 存向量，
   FTS5 做 BM25，SQL JOIN 做 one-hop 图扩展。图库的"generic entity/edge"被换成"8 类叙事学类型化 record"。
2. **8 类 typed records 是 NWM 的灵魂**（论文碾压 Graphiti 的关键）：
   - CharacterState（谁知什么——信息差追踪）

   - NarrativeFunction（视角/读者知晓——dramatic irony 基础）

3. **因果锚点是章节号，不是时间戳**。每条 record 带 source_chapter，写第 N+1 章检索时
   `source_chapter ≤ N`（杜绝未来章节泄漏）。放弃 wall-clock 和故事内时间（论文也不用）。
4. **双 middleware 兜底链（D-D5-1）**：ContextAssembler（静态蓝图）总挂载 + MemoryRecall（动态记忆）
   条件追加。两者前缀不同（"写作前置上下文：" vs "记忆召回："），互补共存。
   MemoryRecall 失败 → return None 降级，ContextAssembler 仍兜底，writing 永不零上下文。

**A2 加固中间件**（绿色，2026-07-20 重构后新增装配，原孤儿代码复活）：
- **ReadCache**：read 缓存 + **写后失效钩子**（write_file/edit_file 后清缓存，避免 edit 闭环失败）
- **EncodingGuard**：写入后**编码合法性 + 内容完整性双校验**（截断文件删除并报错，不让下游消费）；read 降级链只保留 utf-8-sig（移除 latin-1/gbk 防洗白）
- **FileStateTracker**：edit_file 前 old_string 存在性预检（直接拦掉注定失败的 edit）
- **WriteResultInspector**：把 deepagents write 吞掉的 OSError 转抛 `WriteFailedError`，让 ErrorRecovery 能重试

**Trace V2 观测边界**：Harness 的 `ArtifactSnapshotMiddleware` 只在受控写工具成功、回读和 hash
确认后记录跨运行需要复查的稿件；executor 另有平台级 `PlatformArtifactCaptureMiddleware`，独立覆盖
所有真实 creation workload，并把 ToolMessage `status=error` 排除在成功写入之外。两者写入同一幂等
ArtifactRevision 索引，因此不会重复 revision；`/state_log.md`、流式片段和普通读操作不创建 revision。
平台最低取证失败时，普通用户创作保留已写产物但 `evidence_status` 不可消费；A/B、单次测试、
working、snapshot、benchmark 直接收敛为 `evidence_capture_failed`，不得产生有效成绩或进入发布门禁。

**模型传输层重试治理（FR-003/NFR-002，2026-07-29 trace 可见性根治）**：根治"两层重试相乘制造约 18 分钟无解释等待"（EVD-003~005）。治理分三层，单一权威、显式配置、可观测：
- **SDK 层**：`build_writer_model` 显式 `max_retries=0`，关闭 SDK 内部隐藏重试——行为不再随 `openai`/`langchain-openai` 默认值漂移（CON-003）。关键配置（重试预算、超时、SDK 版本）冻结进 trace `run_snapshot.writer_retry`，可随镜像重建复核（RSK-004）。
- **模型层**：`WriterRetryController` 持有单一权威预算——一次逻辑模型调用最多 2 次传输尝试（DEC-003：首次失败后最多自动重试 1 次），错误分类决定可重试性；已收到任意响应增量/usage/tool-call 后中断（部分响应）绝不自动重放（DEC-006）。预算用尽或不可重试时向上返回携带逻辑调用身份/attempt/分类的结构化 `WriterRetryError`。245 秒预算只约束两次"连续无响应"失败链路，持续有进展的健康长生成不受 wall-clock 总限制（RSK-001）。
- **task 防重放（CON-005）**：`task` 工具运行整个子 Agent，重放会重复副作用/计费。平台级 `TaskReplayPolicy` 经 `RuntimeContext.tool_replay_policy` 注入 harness 的 `ErrorRecoveryMiddleware`；命中 `task` 时 `should_retry` 恒为 False，通用错误恢复不重放整个子 Agent，把结构化错误交回 Meta Agent 用新逻辑任务身份显式重新委派。该规则由当前 executor 平台运行时统一保证（覆盖普通创作/单次测试/A·B/风格优化/角色专家），历史 snapshot 源码不变但运行时仍注入同一 policy。
- **可观测（EVD-006 修复）**：原 `TraceMiddleware` 只记录一次 `llm_start` + 最终 `llm_end/llm_error`，SDK 内部重试不可见。现注入领域层 `retry_runner` 包裹模型调用，每次 attempt 失败/退避写一条 `middleware_intervention` 事件（`model_attempt_failed` / `model_attempt_backoff`），让"正在进行第 N 次尝试"在 trace 时间线可见。重试实现定义在领域层（`app.domains.writing.retry`），平台层 TraceMiddleware 只调用、不 import，保持 platform 不依赖 domains 的分层铁律。

```mermaid
    U_Inner -->|"最内层用户中间件<br/>紧贴 SDK tail"| SDK_Tail
    SDK_Tail --> Node

    %% 响应回链（向外）
    Node -.->|"洋葱内→外<br/>逆序 unwrap"| SDK_Tail
    SDK_Tail -.-> U_Inner
    U_Inner -.-> U_Mid
    U_Mid -.-> U_Outer
    U_Outer -.->|"Trace 记 end/duration<br/>ErrorRecovery 捕异常决定重试"| SDK_Head
    SDK_Head -.-> Response(["📤 响应返回"])

    classDef sdk fill:#f3f4f6,stroke:#9ca3af
    classDef user fill:#dbeafe,stroke:#2563eb,stroke-width:2px
    classDef node fill:#fef3c7,stroke:#d97706

    class SDK_Head,SDK_Tail sdk
    class U_Outer,U_Mid,U_Inner user
    class Node node
```

**洋葱模型的关键**：不同 hook 在不同 graph 节点生效，**"链"不是单一管道**：

| Hook 类型 | 生效节点 | 哪些中间件用 | 作用 |
|-----------|---------|-------------|------|
| `wrap_tool_call` | ToolNode | ErrorRecovery / ReadCache / PathGuard / EncodingGuard / FileStateTracker / FileWriteSerialize / WriteResultInspector / Trace | 缓存、校验、加锁、重试、观察 |
| `wrap_model_call` + `before_model` | model 节点 | ContextAssembler / MemoryRecall / Trace | 注入上下文、稳定缓存 |
| `after_model` | model 节点后 | ArtifactValidation | 检查产物缺失→弹回 model |
| `wrap_tool_call` 成功返回后 | 受控写工具 | Harness ArtifactSnapshot + executor PlatformArtifactCapture | 回读已写文件，经 PayloadGate 幂等创建 ArtifactRevision；error ToolMessage 不计成功，严格 workload 失败标 `evidence_capture_failed` |
| `before_agent` | agent 入口 | ArtifactPrerequisite | 校验前置产物存在 |

**ContextAssembler 为什么排最内层**：它要最后定稿送给 model 的消息顺序，
必须晚于上游所有 wrap，紧贴 AnthropicPromptCaching 之前，才能保证缓存前缀稳定。

**两条组装路径**：
- **硬编码**（config=None）：顺序固定如上表
- **配置驱动**（有 config）：middleware 列表由 `build_middleware_list(processors, ctx)` 从 config 构建

**受控系统升级（C3 / FR-004 / EVD-007）**：容器启动时 `docker-entrypoint.sh` 检查镜像 seed
的 `middleware/` 目录，把 seed 有但 repo 没有的承重系统中间件（如 ArtifactSnapshotMiddleware）
合并进活跃 Harness。只新增不覆盖——用户进化改动过的同名文件记为冲突（写入升级日志），
不静默覆盖。这修复了线上 volume 已存在时不更新 seed 导致缺少承重中间件的问题。

**写作生成的五个阶段（对应图中五色）**：

| 阶段 | 做什么 | 归属 |
|------|--------|------|
| **① 装配** | 构建 RuntimeContext + 动态加载 harness + 装配 agent | executor + harness |
| **② 委托** | meta agent 按 goal 自主委托 interview→storybuilding→detail_outline→writing | harness (subagents/) |
| **③ 循环** | 每个 subagent 内部：生成→review→(修订1次)→返回摘要 | harness (factory.py) |
| **④ 回流** | SSE 流式回前端；关键节点触发记忆入图/派生图，受控写成功后由 Harness 快照与平台最低取证幂等记录 ArtifactRevision，同时冻结 executor 代码、依赖锁与 Harness commit identity，终态写 Manifest | executor (streaming + events + trace) |
| **⑤ 收尾** | 正常/interrupt/cancel/credit_exhausted 四路分流 | executor (agent.py) |

**三个关键认知**：

1. **meta 是自主的，不是硬编码编排**。meta agent 读 meta_system prompt 后自己决定
   调哪个 subagent、什么时候调。典型顺序是 interview→storybuilding→detail_outline→writing，
   但这是涌现行为，不是 if-else。
2. **review-revise 循环有硬上限（1 次）**。`RevisionLimitMiddleware` 强制 writing 子代理
   最多修订一次，且修订后**不再二次审查**——防止无限循环。
3. **业务副作用放 WritingEventSink，审计制品快照放受控 middleware**。middleware 抓不到
   DeepAgents subagent task 调度事件，所以只有 sink 能在 storybuilding/chapter 完成时触发记忆入图和派生图；但写入成功后的回读、hash 和 ArtifactRevision 必须贴着写工具执行，避免从可变 workspace 事后补造历史。

**styling 是前置配置，不在生成流里跑**：`domains/writing/styling/` 在装配阶段（①）
被消费——从 store 读激活风格的 4 个字段，填进 ctx.styles，包内 `apply_style_suffix`
追加到各 subagent 的 system_prompt 末尾。
